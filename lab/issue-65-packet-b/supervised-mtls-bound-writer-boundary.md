# Root.ark #65 — supervisor-owned mTLS PUT + bound PostgreSQL ciphertext

**Status: `LAB_ONLY_NON_AUTHORIZING`.** This is a disposable single-host physical I/O experiment. It is not imported into Root.ark's normal HTTP server, changes no production storage routes, and authorizes no live transfer, migration, provider, release, or product Zero-Knowledge claim.

## Reproduction

With Docker Desktop, locally cached `postgres:18.6-alpine3.24`, Windows Node 24 and WSL Node 22:

```powershell
node lab/issue-65-packet-b/run-supervised-mtls-bound-writer.js
```

The runner creates an isolated PostgreSQL 18 container published on a random **127.0.0.1-only** port, loads the already-existing `db/zk1-gate-authority.sql`, and provisions independently restricted gate, STOP and writer SQL logins. Each integration test creates another unique writer login, fixture account/compartment/keyring, signed STOP identity and ephemeral CA/server/client certificates. Private TLS keys remain in the local temporary fixture and trusted IPC; no certificates or credentials are committed. The runner only deletes its own container after checking immutable ID and exact disposable labels. Both native Windows Node and WSL Node 22 run identical real-PostgreSQL tests; on other platforms the native run remains available.

## Physical authority and observed ordering

One supervisor-owned direct `ChildProcess` owns **both** the real TLS listening socket and the real PostgreSQL session that invokes `zk1_gate.write_bound_chunk(index,ciphertext)`. The parent is the exclusive local operator: its independently pinned Ed25519 host signer identifies that exact process/epoch/PID; its verified restricted gate SQL login performs START and inserts the immutable `writer_binding` for a unique PostgreSQL writer `session_user`. PostgreSQL enforces the exact admission, worker, scope, object and generation and rejects privileged writer identity overlap. The child receives the writer login credentials and bounded TLS material over its supervisor-owned IPC **after** START and binding, and verifies its writer-role privileges before opening the socket. The STOP signer and gate/STOP SQL credentials never enter the child process environment.

The trusted operator separately supplies the authorized client certificate (outside HTTP); the controller hashes its DER bytes with SHA-256, binds the **same fingerprint** to the admission `principal`, and passes that pinned fingerprint over trusted IPC. The child requests a valid TLS 1.3 client certificate, checks successful certificate-chain authentication **and exact constant-format SHA-256 fingerprint**, and only accepts bounded `PUT /fixture-chunk/<index>` over `127.0.0.1`. HTTP headers/body cannot choose the account, compartment, admission, generation, child PID, cert fingerprint or SQL login. Arbitrary/absent client certificates and synthetic host-identity headers cannot override the pinned identity. This is a test certificate, not a proof of live trusted-device enrollment or current revocation status.

The child begins a real PostgreSQL READ COMMITTED transaction, checks `verify_chunk_writer_binding`, and calls **the already-existing** `write_bound_chunk`. That SECURITY DEFINER SQL effect holds `head FOR UPDATE` through COMMIT/rollback. The disposable harness explicitly holds a real, uncommitted transaction, starts `beginQuiesce` in another gate session and observes that closure cannot overtake the child SQL row lock. After the test releases the transaction, either the chunk commits first or child death rolls it back; only then can QUIESCING commit. An HTTP 200 is withheld until a separately restricted parent gate SQL login **reads the persisted exact ciphertext and compares SHA-256 against the child's reported bytes**. Lost readback, process death or ambiguous commit cannot generate a success response. The parent and child may know ciphertext, but never plaintext keys.

For quiescence, the independently pinned supervisor kills the **actual child owning the TLS socket and SQL connection**, observes both OS `exit` and `close`, signs an exact process/admission/generation STOP statement, records it with the independently restricted STOP SQL identity, then authorizes gate `FINISHED` and `PENDING`. Tests also cover a client abort after SQL insertion but before COMMIT (rollback), SIGKILL during the physical transaction (rollback and row-lock release), attempted late/replayed PUT, wrong client certificate, wrong operator principal/PID, and premature FINISH/PENDING denial.

## Boundaries and outstanding work

The proof covers only a **single direct** local child, a **single explicitly operator-bound writer** and its own TCP/PG sockets. It cannot certify independent physical stopping of subprocess descendants, remote S3/Drive/GET/WebDAV, replication/failover, cloud egress, peers' TCP buffers or bytes already emitted. No live device, fresh external witness, independently hosted status authority, multi-host operator, post-restart process adoption or emergency recovery authority is proven. The gate, writer and STOP SQL logins are separate restricted identities but use one disposable PostgreSQL instance; this does not establish organizational or regional independence.

TLS handshake and writes can race a quiesce transition. **Safety for the committed PostgreSQL ciphertext effect specifically derives from the SQL row lock held inside `write_bound_chunk`**, not from a stale HTTP-side admission check. An already-completed transaction can produce an independently verified success after QUIESCING closes; its effect was ordered before the transition. If a client disconnects after COMMIT but before receiving HTTP 200, its delivery outcome is unknown, although the durable ciphertext may exist; replay with the same bound index fails closed. Fixture body size is capped at 4 KiB and one attempted chunk per process; this does not establish production chunk sizes, rate control or stream behavior.

Current production strict HTTP routes must continue returning 503 for scopes requiring physical STOP. Promotion to any real remote endpoint requires an independently approved trusted client/witness chain, selected provider-specific data-plane fencing, resilience to parent/supervisor restart, independent review and exact protocol acceptance. The laboratory must not be used as a production authorization shortcut.
