# Local development setup

Root.ark loads values from `.env` at startup when that file is present. Copy `.env.example` to `.env` and set a private `JWT_SECRET`; never commit `.env` or other local secrets.

Generate a fresh secret and start the application:

```powershell
$env:JWT_SECRET = node -e "process.stdout.write(require('crypto').randomBytes(32).toString('hex'))"
npm start
```

```sh
JWT_SECRET="$(node -e 'process.stdout.write(require("crypto").randomBytes(32).toString("hex"))')" npm start
```

Set `PORT` separately if a port other than the default is needed.

## First user bootstrap

With no existing users, startup fails closed unless a valid seed or explicitly enabled development bootstrap is configured. For a clean install, prepare `data/users.json` with users whose usernames are unique after trimming and lowercasing and whose passwords are bcrypt hashes with a cost of at least 10. Use distinct, private passwords that are at least 16 characters long. Set `ROOTARK_BOOTSTRAP_USERS_FROM_SEED=true` for the one-time import in every environment, then remove the opt-in. Startup rejects the published sample passwords (`admin123` and `user123`) in every environment except `NODE_ENV=test`, regardless of username pairing. The `/users` create and update routes also reject attempts to set either sample password, and the shared user-save boundary enforces the same rule.

On a clean `NODE_ENV=development` install, enable `ROOTARK_DEV_BOOTSTRAP_DEFAULTS=true` and provide distinct, private passwords through `ROOTARK_DEV_BOOTSTRAP_ADMIN_PASSWORD` and `ROOTARK_DEV_BOOTSTRAP_USER_PASSWORD`. Each must be at least 16 characters long and must not equal either published sample password. Without both secure values, startup fails before creating the local users file. These values are hashed into the local account store; remove the bootstrap environment variables after creation. The predictable `admin`/`user` fixture passwords are available only when both `NODE_ENV=test` and `ROOTARK_DEV_BOOTSTRAP_DEFAULTS=true` are set. Never use test fixtures or development accounts for deployment.

For a production deployment, set `NODE_ENV=production` and import a secure, hashed user seed with `ROOTARK_BOOTSTRAP_USERS_FROM_SEED=true`. Verify the intended secure admin account can sign in, then remove the opt-in and seed file according to your deployment process. Fresh production startup without users remains fail-closed. The listener may be behind a reverse proxy, so loopback binding is not treated as protection from remote clients forwarded by that proxy. Use secure account passwords and restrict origin ingress at the network/proxy layer; a trusted-proxy setting only governs forwarded request metadata and does not restrict who can reach the proxy.

The seed import and local bootstrap are separate paths: seed import always requires its explicit opt-in, test fixtures require `NODE_ENV=test` plus their opt-in, and development bootstrap requires its own opt-in plus both secure passwords. Authentication throttles, login challenges, and TOTP replay state are process-local. Run exactly one application process; startup rejects `ROOTARK_RESTORE_INSTANCE_COUNT` values other than `1`. This setting is a declaration, not replica discovery, so deployment configuration must also prevent an unreported second process. Multi-process authentication remains unsupported until shared transactional auth state is implemented.

## Chunk-upload staging capacity

Set `CHUNK_UPLOAD_STORAGE_TOPOLOGY=single-host-local-volume`, `CHUNK_UPLOAD_QUOTA_PER_ACCOUNT_BYTES`, `CHUNK_UPLOAD_QUOTA_SYSTEM_BYTES`, `CHUNK_UPLOAD_QUOTA_PER_ACCOUNT_ENTRIES`, and `CHUNK_UPLOAD_QUOTA_SYSTEM_ENTRIES` before enabling `/upload-chunk`. All four limits are required positive safe integers with no defaults; each per-account limit must not exceed its system limit. Missing, malformed, or contradictory byte or entry limits disable chunk uploads while the rest of the application remains available. The topology value is a required operator attestation that all application workers which can write this staging tree run on one host and use the same reliable local volume. It does not discover replicas, bind mounts, container placement, or mapped drives; deployment automation must enforce the attested topology. On Linux, startup also rejects known NFS, SMB/CIFS, FUSE, 9p, Ceph, AFS, and NCP filesystem types. On Windows, UNC paths are rejected; a mapped network drive cannot be identified reliably by the application and must not be used. If the topology cannot be established, omit the setting so chunk uploads remain disabled. Choose byte limits from the real host's available staging and disk budget; choose entry limits from the maximum number of concurrent/incomplete sessions and per-request operations the host can safely retain. The example environment intentionally provides no capacity values. The smallest usable byte limit must be at least the 8 MiB maximum reservation made before parsing each chunk request. During completion, budget for about twice the assembled file size because accepted parts and the assembled copy coexist, plus encryption overhead and any other concurrent requests still holding their full 8 MiB incoming reservations; the completing request's reservation shrinks to its actual part size before assembly is reserved. Encryption currently reads the complete assembled file into a Node.js memory buffer, so provision worker RAM for the largest encrypted completion and expected concurrent completions as well; the disk quota is not a memory limit. Filesystem metadata and directory overhead also consume disk but are outside the byte ledger. The entry ledger counts every live operation row, including zero-byte parts and incoming or assembly operations, plus one row for each upload session directory. Both account and system limits are checked in the same SQLite write transaction. Expiring a session releases its part-operation rows but keeps the session entry while the seven-day tombstone blocks stale retries; the session entry is released only when that directory is removed. Metadata-only, empty, and expired-tombstone directories therefore consume entry capacity as well. A legacy tombstone or empty directory whose owner cannot be proven is charged to one shared conservative account bucket and still counts against the system limit. One-part empty files remain valid when both the byte and entry budgets have room. On restart, the ledger checks existing counts against the configured caps in its initialization transaction. If an already-valid ledger is above a newly lowered cap, it remains available for expiry cleanup, and new reservations are refused until the retained entries fit the configured limits. These limits bound the amount of metadata and the number of session directories the service can accumulate; they do not measure exact filesystem bytes used by SQLite, JSON metadata, or directory allocation. This cap covers temporary chunk parts and incoming writes; it does not limit final stored files, total `temp/` usage, or request rates.

The quota ledger is a separate SQLite file under `temp/.chunks` and requires the ledger plus all chunk staging directories to share a reliable local volume on one host. Any participating processes must use the same absolute runtime paths, including both `temp/.chunks` and the `data/.rootark-cloud-file-locks` directory derived from the same working directory; using separate working directories or mount aliases can split the file-lifecycle locks even when they reach the same underlying volume. Multi-host, NFS, SMB, and other unverified network staging are unsupported. The application cannot discover all deployment replicas or volume mappings; the setting is an operator attestation, not a distributed coordination guarantee. Linux detects and rejects the listed filesystem types, but this list cannot prove that an unknown filesystem is local. The quota ledger uses SQLite transactions and session locks across same-host processes with those identical paths. The application as a whole still requires exactly one process because authentication and other state remain process-local. Stop all old application processes before enabling this feature on a deployment with existing chunk sessions. On POSIX, every path ancestor must be owned by the service identity or root and must not be writable by an untrusted group/user unless a sticky bit protects its entries; the staging directory itself must not be group/other writable. Unsafe paths disable chunk uploads. On first initialization, validated legacy session metadata and regular numbered parts are imported atomically; unsafe, untracked, over-budget, or unattributable files keep only chunk uploads disabled until repaired. On restart, only dead-owner operations are reconciled; files with ambiguous state are preserved and fail closed. The seven-day session expiry remains inactivity-based and never reclaims quota by age alone.

On Windows, place the application under an existing local parent whose ACL prevents untrusted local principals from deleting the parent or its children, or changing its owner or DACL. Every ancestor from that parent to the volume root must be non-reparse and must not grant untrusted principals `DELETE`, `DELETE_CHILD`, `WRITE_DAC`, or `WRITE_OWNER` on the ancestor itself. Inherit-only ACEs that do not apply to the ancestor are not used for that decision. Ancestors may be controlled by the service identity, `SYSTEM`, local `Administrators`, or Windows `TrustedInstaller`. The service creates a missing `temp/.chunks` directory atomically with a protected DACL granting full control only to the service process identity, `SYSTEM`, and local `Administrators`; chunk directories, files, SQLite data, and sidecars must inherit or verify those same trusted principals. The Windows temporary directory is not a supported staging parent. If an existing root, descendant, owner, or ACL is permissive, contains a reparse point, or cannot be verified, startup preserves the tree and disables only chunk uploads. The application does not repair existing ACLs or change shared OS temporary-directory ACLs; move or secure the staging tree under a suitable parent before restarting.

## Reverse proxy and client IP

Leave `TRUSTED_PROXIES` unset when clients connect directly. When a reverse proxy is used, list only the explicit IP addresses or CIDR ranges for trusted proxy peers in the request chain, including the immediate socket peer and any expected intermediate proxy hops; do not use a hop count or a catch-all range. Express uses this configured chain to derive the client IP and forwarded protocol used by authentication throttles, security audit attribution, WebSocket origin checks, and origin-sensitive share actions. The proxy chain must remove or safely replace caller-supplied forwarding headers, and the origin network must prevent untrusted clients from reaching the app around the proxy. Validate the actual multi-hop chain end to end. If Cloudflare is in the path, follow the current [browser session and proxy trust model](security/browser-session-threat-model.md), restrict origin ingress to the intended Cloudflare ranges, and recheck Cloudflare's published ranges when the topology or allowlist changes. Repository configuration cannot verify a live deployment's ingress. Neither trusted-proxy configuration nor loopback binding prevents remote access when a reachable proxy forwards requests; published sample passwords are therefore prohibited outside test regardless of the listener path.

The raw WebSocket upgrade is guarded before `101` and resolves upgrade-rate and concurrent-connection budgets through the same configured trust function as Express. Direct untrusted peers are keyed by their socket address; across a configured proxy chain the nearest untrusted forwarded hop identifies the client, while caller-supplied prefixes farther to the left are ignored. Ensure proxies strip, replace, or safely append `X-Forwarded-For` as described above. These limits are process-local, so multi-instance deployments also need a shared edge limit. Set `NODE_ENV=production` for production so session cookies use `Secure`; production startup rejects `SESSION_COOKIE_SECURE=false`, and `/ready` remains unavailable when the effective session-cookie policy is insecure.
