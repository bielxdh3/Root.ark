# Whole restore transaction boundary

Whole restore uses a durable, local rollback protocol. It does **not** provide instantaneous atomic visibility across JSON files, quarantine, uploads, SQLite, and cloud providers. Before replacing local state, Root.ark stages and verifies preimages for every locally controlled destination the archive can change. If the process stops before the local commit boundary, startup restores those preimages before migrations or request handling. Cloud-provider effects remain outside that local rollback domain.

## Admission and service barrier

Restore takes the shared backup-operation lock, validates the full staging-root and backup-ID path (including symlink/junction checks), then writes a `preparing` coordinator at `data/.rootark-restore-coordinator.json` and drains active work before creating the pre-restore backup. The HTTP gate runs before body parsing, static files, and routes. Each admitted HTTP request holds a lease in `data/.rootark-active-requests/`. Long-running cloud trash, cloud restore-sync, WebDAV reconciliation, fire-and-forget cloud writes, and cleanup workers use the same gate. A restore waits for their leases. A lease-directory error or bounded quiescence timeout aborts before restore destinations change.

Leases are not removed based on local PID checks because PIDs do not identify the same process in every container or host sharing a volume. A crash may leave a stale lease and make a later restore time out. Stop every instance using the shared runtime, verify that no operation remains active, and remove only confirmed stale lease files as an operator action.

The supported server topology is one application process per runtime. Startup rejects `ROOTARK_RESTORE_INSTANCE_COUNT` values other than `1` before creating restore leases or reading restore state because authentication throttles, challenges, and TOTP replay protection remain process-local. The restore service retains a multi-instance acknowledgement protocol, but that protocol does not make multi-process authentication safe. Do not deploy extra replicas or set a count greater than one until auth state has shared transactional storage. The setting is not replica discovery, so the deployment must enforce the single-process topology.

The shared operation lock uses exclusive file creation and records its owner instance ID. A lock owned by another instance, or an older lock without an instance ID, is treated as active; visibility of a local PID cannot prove a process in another namespace has stopped. Stop all instances and verify that no operation remains active before removing a stale lock.

## Local preimage and commit protocol

After archive, manifest, checksum, path, entry, and quarantine validation, Root.ark constructs the preimage plan and stages these local domains before the first restore mutation. The staging root and backup-ID child are validated before coordinator creation, then checked again before deleting or writing staging files. Symlink/junction ancestors and an aliased backup-ID staging directory fail closed without creating a restore barrier.

1. `quarantine.json` and the configured quarantine payload tree, when quarantine state is present in the archive;
2. JSON state files present in the archive that restore will replace, the local backup-history state, the restore-provider-orphan policy, and its durable initialization marker;
3. the complete `uploads/` tree when the archive contains an uploads tree;
4. the SQLite database and its configured sidecars when SQLite is enabled.

Preimage staging rejects symbolic links, hard-linked files, unsupported filesystem entries, changed files, and failed checksums. Staged files are copied through exclusive creation and hashed. A manifest records the exact paths, prior existence, file hashes, and directory entries; its SHA-256 digest is stored in the coordinator. On POSIX, staged files and directories are flushed before the coordinator advances to `prepared`. Windows does not expose a portable directory-entry flush through Node.js, so this does not claim power-loss durability on Windows.

Only after the complete preimage is verified does the coordinator move from `preparing` to `prepared`, and restore begin changing local state. Before writing `restart_required`, restore flushes each restored ordinary data file and each file and directory in the restored uploads tree; quarantine and SQLite retain their own flush paths. Rollback likewise flushes restored preimage files and their affected directories before advancing rollback progress or writing `rollback_complete`. On POSIX, directory `fsync` failures propagate and keep the coordinator short of its durable marker. Node.js directory `fsync` is unsupported on Win32; the coordinator records `directorySync: "unsupported"` there, and recognized unsupported file-flush errors are tolerated for compatibility. This is not a cross-platform power-loss durability guarantee. The `restart_required` phase is the local process-recovery commit boundary: provider reconciliation can proceed only after the restored state has restarted successfully.

When cloud storage is enabled, restore obtains a complete provider inventory before local mutation. Inventory failure aborts before commit. Provider objects not certified by the selected archive become area-specific entries in `data/.rootark-restore-provider-orphans.json`; same-named objects in different areas have distinct identities. A durable `.rootark-restore-provider-orphans-state.json` marker distinguishes an initialized empty policy from a lost policy. Once the marker exists, a missing, malformed, or unsupported policy blocks affected file access and startup rather than treating the provider inventory as empty. Startup creates an explicit empty policy and marker for a new runtime and upgrades a valid legacy policy without dropping entries. Both files participate in local pre-image rollback and are excluded from backup archives and restore input. For `cloud_complete: false` archives, same-name provider objects are suppressed because the archive cannot establish that their bytes match. The policy is committed before `restart_required` and participates in the same local pre-image rollback. Ordinary file read/edit authorization and public-share delivery deny suppressed uploads. A suppressed temp payload is not hydrated, previewed, or approved, even when stale bytes remain in the local cache. Its restored pending metadata is preserved and appears in `/pending` as `restoreOrphan: true` with `availability: "recovery_required"`; an authorized approver can reject it without fetching its payload, or the uploader can send a fresh upload under the same name. A fresh pending upload clears temp suppression after the new local bytes and durable temp upload intent are registered.

A local-only restore marks provider inventory `unknown` and records the selected backup ID. Cloud-disabled local service may continue. Before cloud-enabled startup opens the application listener or trusts provider inventory, it validates the selected archive, requires `cloud_complete: true` as a complete upload baseline, inventories the current local upload tree, durably queues the current local bytes, and inventories the provider. If the selected archive is incomplete, reconciliation remains blocked with instructions to select a complete backup through `ROOTARK_PROVIDER_INVENTORY_BASELINE_BACKUP_ID`; it does not certify a partial delta. Files deleted locally are not uploaded again; remote objects left by deletion remain suppressed by the resulting policy. A rename is handled as a new local upload while the old provider object remains suppressed. Reconciliation streams from existing local files and does not create an untracked temporary copy of archive payloads. The durable queue stores a local-tree fingerprint and source hashes; a changed provider context or local tree resets stale completed entries and Google Drive file ID pins before retry.

A reconciled inventory marker is bound to a one-way hash of the configured provider namespace and authenticated principal. AWS S3 resolves identity through STS `GetCallerIdentity` and normalizes assumed-role sessions to the stable role ARN, so session-name rotation for the same role does not invalidate the marker. Google Drive uses `about.get`'s stable permission ID. Custom S3-compatible endpoints do not expose a standard account-identity API, so they require a stable operator-supplied `AWS_S3_PRINCIPAL_ID`; the access key ID is not used as identity. Credential material is not written to the marker. Identity is refreshed before and after guarded cloud operations; startup reconciliation and the scheduled restore-sync worker also bind each upload and inventory attempt to the context resolved for that run. If the identity changes during an upload, the entry remains retryable and suppression is retained; startup reconciliation cannot certify inventory. This detects refreshed credentials when they resolve to a different account or role, but does not make the provider operation and local marker update atomic. If identity cannot be resolved, startup remains blocked. Changing the provider, principal, bucket or folder, endpoint, region, default root mapping, or prefix invalidates the marker and requires reconciliation before cloud access. A cloud-disabled startup persists this invalidation and retains the selected baseline. Retention, explicit deletion, and unresolved-marker writes take the same provider-policy lock. A marker write verifies that its selected archive still exists while holding that lock, so deletion-first leaves no dangling baseline and marker-first protects the archive from deletion or retention. A legacy reconciled marker without a provider context is treated as unknown; if its archive has been deleted, an operator must explicitly select a replacement with `ROOTARK_PROVIDER_INVENTORY_BASELINE_BACKUP_ID`. Startup validates that archive before replacing the old marker baseline and never guesses the latest backup. When persisted sync entries have a future lease or retry deadline, startup waits until the earliest deadline, resumes due entries, and inventories only after every selected upload succeeds; the retry delay is capped at one hour. If a provider attempt fails, startup exits fail-closed with the durable queue intact for the next start. A failed or missing baseline, queue, identity, or provider inventory keeps cloud access blocked. The queue and marker are runtime state and are not copied into archives.

Older `restart_required` coordinators lack an explicit provider-policy flag. Their empty `providerReconciliation` list cannot prove that cloud inventory was skipped: a cloud restore with no provider sync work has the same list shape. Startup therefore requires the suppression policy for every legacy pending restore and blocks if it is missing. Markerless legacy inventory state also needs the operator to select a baseline explicitly with `ROOTARK_PROVIDER_INVENTORY_BASELINE_BACKUP_ID`; initializing an empty policy or guessing a backup could expose provider objects. Resolve these cases only after verifying the deployed provider topology and backup contents; do not remove the coordinator or create an empty policy blindly.

If preimage creation stops while the coordinator is `preparing`, no restore destination has changed. Startup clears the partial preimage and coordinator only after it acquires the restore lock. If a failure or process interruption occurs while the coordinator is `prepared` or `rolling_back`, startup verifies the preimage and restores domains in reverse order, resuming safely after interruption. It performs SQLite and quarantine journal recovery before applying the whole-restore preimage. Replaying a domain restore is idempotent. After all local domains are restored, the coordinator durably advances to `rollback_complete` before deleting rollback material. A later startup in that phase retries cleanup without depending on the already-restored preimage manifest, so partial cleanup cannot turn a completed rollback into an unrecoverable manual-recovery state.

If rollback itself fails, Root.ark records `manual_recovery` when possible and refuses to serve traffic. A later startup revalidates the entire preimage manifest and all staged hashes before retrying the idempotent rollback. This recovers from transient storage errors without applying an unverified preimage. If validation or rollback fails again, the barrier remains active. Stop all instances sharing the runtime, preserve offline copies of the coordinator, the transaction's `.restore-preimages/<transactionId>` directory, `data/`, `uploads/`, and the configured quarantine tree, and fix the underlying storage or permission fault before one controlled restart of the configured instance set. Do not delete or edit the coordinator or preimage, and do not treat the pre-restore ZIP as a replacement for the verified preimage. If the preimage is missing/corrupt or a retry still fails, Root.ark has no self-service recovery command; keep the service stopped and use maintainer-assisted recovery. Tests inject failures at each local stage and use disposable data only.

While the restore and rollback protocols gate application traffic and background workers, they cannot provide one atomic filesystem transaction across different filesystems or protect against external writers that bypass the application gate. Other instances must use the shared gate and locks. Rollback itself is a compensating operation: clients or external processes outside the application may observe intermediate filesystem changes.

## Restart and external-provider reconciliation

When the persisted inventory marker is otherwise `known`, a context-resolving cloud adapter checks nonterminal restore-sync queues before startup completes. A queue whose saved provider context is missing or differs from the current identity makes its archive a candidate reconciliation baseline. If exactly one queue needs rebinding and cloud is enabled, Root.ark validates that archive, rebuilds the queue from its archived bytes plus the current local delta, and binds the new queue to the resolved identity before any upload. If that archive is missing or incomplete, an explicit complete baseline is required. The selected replacement backup durably records the legacy queue it supersedes before the inventory marker moves; startup retires that queue only after its active lease expires, then clears the reference. An interrupted startup can therefore resume the retirement without selecting the old queue again. If multiple queues need rebinding, startup fails closed with `LEGACY_RESTORE_SYNC_AMBIGUOUS`; no arbitrary backup is selected and no provider upload begins. If rebinding is needed while the provider is disabled, Root.ark marks inventory unknown and leaves the queue blocked. Completed and cancelled queues are ignored.

After local commit, the coordinator changes to `restart_required`. In the supported single-process topology, restart the server once; it loads restored state, runs required migrations, and acknowledges only after its listener binds. Before clearing the coordinator, the service retries removal of the transaction's extracted staging directory. A cleanup error keeps the barrier active for a later restart. HTTP returns 503, and realtime clients are closed until the acknowledgement and local staging cleanup succeed. Provider reconciliation workers stay behind the same barrier. A coordinator created for a multi-instance deployment cannot be acknowledged by this server build; preserve it and use an operator-led recovery plan rather than deleting it.


If a migration fails before the listener binds, startup fails closed: the coordinator remains `restart_required` and its preimages remain available. Each migration runs in its own SQLite transaction, so the failed migration's partial changes roll back; any earlier migrations that committed remain recorded and the next startup retries the remaining migrations. This is forward retry after the restore commit, not automatic rollback to the pre-restore state.

The regression `test/backup-restore-transaction-boundary.test.js` (merged in PR #110, merge commit `7bc9e81a1496041b3d75c5bd3cd359a603c6f6a8`) exercises the service-level multi-instance coordinator acknowledgement protocol: a duplicate acknowledgement from `replica-a` is counted once; a distinct acknowledgement from `replica-b` reaches the required count and clears the coordinator barrier. The test uses disposable runtime state and verifies coordinator acknowledgement counting only; it does not validate provider dispatch, the supported single-process startup gate, or live provider interoperability.

Cloud-provider actions cannot participate in one portable transaction with local files and databases. Once the local commit barrier clears, a provider outage may leave durable work pending or failed while local restored state remains authoritative. Retries use operation IDs and leases. Google Drive restore entries persist a stable generated or existing file ID before upload; retries target that ID after verifying the Root.ark key and configured parent. S3 retries use the same deterministic object key. This is resumable reconciliation, not distributed atomicity. Live provider credentials were not used for validation.

Local provider reconciliation applies the same path/name exclusions as backup collection, prunes excluded directories, and excludes the configured quarantine subtree, its real-path aliases, and hardlinks to known quarantine payloads. A hardlink on any otherwise eligible upload path fails reconciliation before provider uploads begin. This prevents an ordinary filename from bypassing the backup exclusion of a sensitive target such as `.env.*`, `service-account`, `credentials`, `.key`, `.pem`, `.p12`, or `.rootark-cloud-cache-*`. These are path-based exclusions, not content inspection.

Restore reconciliation uploads archived `uploads/` entries; it does not delete provider objects absent from that archive. For a complete cloud archive, only provider identities absent from the selected archive are suppressed. For an incomplete cloud archive, all inventoried `uploads` and `temp` objects are suppressed until selected archived upload bytes successfully reconcile; this prevents same-name stale provider bytes from being trusted or hydrated. The suppression identity includes area, so archived temp manifest entries cannot collide with same-named uploads. The current restore validator rejects archives containing `temp/` entries before local mutation; Root.ark does not restore temp payloads. Suppression does not change the legacy missing-ACL default for unrelated files. Temp suppression also prevents automatic cache-queue reuploads from resurrecting a stale pending object. This is a local access boundary, not a provider mirror: an out-of-band provider writer can create new objects after inventory, and provider cleanup remains a separate authorized and audited operation. The external provider still cannot join the local rollback transaction. After local commit, provider reconciliation remains durable and retryable with exponential backoff capped at one hour; stale provider objects stay suppressed until the selected archive bytes upload successfully. A provider outage therefore delays availability of affected files while local restored state remains authoritative. Until an incomplete archive's selected objects finish provider reconciliation, their local files remain inaccessible to ordinary users as well as their stale provider copies; managers retain the documented recovery review path.

The disposable regression `provider upload failure survives restart and retry keeps the provider object idempotent` injects a provider outage, verifies the persisted retry state, interrupts a worker after writing the deterministic provider key but before completion is committed, and confirms a restarted worker retries the same logical key and completes without another upload after completion. This validates the retry state machine against a fake provider; it does not establish live S3 or Google Drive interoperability.

An archive can include files under `temp/` only when `BACKUP_INCLUDE_TEMP=true` or `BACKUP_INCLUDE_PENDING=true`; `temp/.chunks/` and `temp/.incoming/` remain excluded. The current restore validator rejects an archive containing temp payloads; pending payloads are not restored and must be uploaded again. If restored pending metadata points to a provider-only temp payload absent from the selected archive, Root.ark preserves the metadata as recovery-required but suppresses the payload; an approver can reject the stale item without hydration, and a fresh local upload registers a durable temp intent before clearing suppression. The ZIP manifest records archived bytes; it does not promise that ephemeral temp state is restored. The provider-orphan policy is excluded from future archives, so provider names observed during restore are not copied into later backup contents.

The disposable regression `restore provider reconciliation remains retryable after five failures and restart` injects five provider failures, verifies persisted capped-backoff retry state, restarts a worker, and confirms the sixth attempt reconciles the selected bytes and clears suppression. `abrupt exit during partial whole-restore pre-image creation cleans preparing state` and `restart rolls back crashes inside quarantine journal and commit boundaries` use child-process exits to validate cleanup and rollback from partial preimage and quarantine-journal stages. All fixtures are temporary and use fake providers.

## Durability and recovery limits

### Recovery-artifact compatibility

New whole-restore coordinators use version 4 with pre-image manifests version 2; the only legacy pair accepted for automatic rollback is coordinator version 3 with manifest version 1. Mixed or otherwise unsupported pairs fail before any restore domain is rewritten and retain the startup barrier for manual recovery. Version-2 tree snapshots record the source root directory mode as well as entries. Recreated POSIX entries are owned by the restoring service account, so rollback adds the source group permission bits to the new owner bits (for example, `0070` becomes `0770` and `0060` becomes `0660`) while preserving group and other bits. This preserves service access when the original tree used group permissions, but ownership itself is not restored. Version-1 snapshots did not record the root mode, so a legacy rollback can restore the entries but cannot prove or restore the former root mode; recovery reports `legacyRootModeUnverifiable` for that case.

New SQLite restore journals use version 2 and record SHA-256 hashes for each original database/sidecar that existed before replacement. Recovery verifies the rollback copy or already-restored destination against that hash before replacing data. A version-1 journal can be rolled back automatically only when its original hashes are present and valid; a committed version-1 journal may be cleaned up without hashes because it no longer needs rollback data. An interrupted version-1 journal without original hashes fails closed, keeps the journal and service barrier, and requires manual recovery rather than guessing which database bytes are original.

SQLite recovery-journal updates also use a fresh, exclusive same-directory temporary file, flush it, and atomically rename it over the primary journal. If writing an update is interrupted, the previous committed journal remains authoritative; a crash-left temporary is not replayed as the primary journal and may remain as an unreferenced file. On POSIX, directory `fsync` failures propagate and keep recovery fail-closed. Node.js does not provide portable directory-entry sync on Windows, so the same durability guarantee is unavailable there.

Coordinator and acknowledgement records use same-directory temporary files, file `fsync`, and atomic rename. Preimage files are flushed before the `prepared` phase. Restore destination files and directories are flushed before their coordinator progress/commit markers where the platform supports those operations. This does not form one durable transaction across all filesystems, and it does not promise recovery from sudden power loss or storage-controller failure. Node.js does not provide a portable directory-entry flush on Windows, so Win32 has a weaker power-loss boundary even when the file flush succeeds. The rollback protocol is not a cross-filesystem transaction.

Large preimages require free space for a copy of the local state being replaced. Insufficient space or a staging error fails before restore mutation. Full rollback can still fail because of later storage errors, permissions, interference by an external writer, or an unavailable filesystem; those failures keep startup blocked for manual recovery. Cloud-provider state is outside rollback and may require retries after the local commit. These boundaries are tested with temporary runtime directories; no real user data is used.
