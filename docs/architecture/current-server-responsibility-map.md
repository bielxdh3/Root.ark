## 2. Server composition summary

`server.js` is the integration spine. It is 7,900 lines and currently owns startup, configuration, filesystem layout, persistence adapters, authorization helpers, cloud adapters, realtime setup, most route families, lifecycle coordination, and background workers (`server.js:1-43`, `server.js:45-165`, `server.js:7884-7900`).

Existing partial boundaries are present for:

- authentication routes and login throttling: `src/routes/auth.js`;
- analytics, audit, backup, and trash route registration: `src/routes/{analytics,audit,backups,trash}.js`;
- HTTP and realtime authentication: `src/middlewares/auth.js`;
- permission middleware: `src/middlewares/permissions.js`;
- repositories for users, folders, uploads, sharing, permissions, expirations, versions, encryption metadata, analytics, audit, history, backups, and trash;
- backup, restore, trash, cloud-storage, preview, and backup-scheduler services.

The following remain primarily inline in `server.js`: users/folders/file-access routes, uploads and scanning, previews and encryption routes, file versions, public links, WebDAV, file rename/move, and the realtime server itself. Route registration passes large callback contexts into the partial modules (`server.js:4492-4504`, `server.js:7278-7333`), so those modules reduce route size without removing the central dependency graph.

Startup creates the HTTP/WebSocket servers, validates `JWT_SECRET`, configures JSON/static middleware, creates local runtime directories, runs SQLite migrations when enabled, seeds users/folders, schedules backups, repairs/cleans temporary data, starts cloud-trash/restore retry work, and listens on the configured port (`server.js:45-165`, `server.js:4322-4438`, `server.js:7884-7900`).

## 9. Recommended first extraction

### Candidate

Extract the current WebSocket transport and notification fan-out boundary: authentication at upgrade, client lifecycle, heartbeat/idle handling, message validation/rate limits, freshness checks, `sendRealtime`, `broadcastRealtime`, and `broadcastDataChanged`.

### Proposed target boundary

Create a small CommonJS realtime module, for example `src/realtime/server.js`, with injected dependencies for `WebSocket`, cookie parsing, expected-origin calculation, current-user authentication/freshness, runtime limits, and the HTTP server. It should return the transport lifecycle and broadcast functions. `server.js` should retain thin compatibility adapters so existing route producers continue emitting the same event names, payloads, and timestamp envelope.

### Expected files to move or change

- `server.js`: move only the WebSocket construction/lifecycle block (`server.js:52-65`, `server.js:263-287`, `server.js:4401-4438`) and pass the returned broadcaster to existing route contexts/callers.
- New `src/realtime/server.js`: own transport lifecycle, connection authentication, heartbeat, freshness, rate and payload bounds, and event fan-out.
- Tests: add the missing focused contract tests listed below before moving code. No tests are added by this Phase 4.0 map.

### Invariants to preserve

- Cookie-only browser WebSocket authentication; no bearer token in the URL.
- Expected-Origin validation before the `connected` event.
- HS256 claim validation, current user lookup, disabled/deleted rejection, `sessionVersion` comparison, and expiry enforcement before each authenticated message/send.
- Maximum payload and buffered bytes, disabled compression, binary-message rejection, per-window message limit, heartbeat, idle timeout, and close cleanup.
- Exact `{event,payload,timestamp}` envelope and `data:changed` source/payload shape.
- Existing producer calls and route response behavior; no event is emitted to unauthenticated or stale sockets.

### Explicit exclusions

Do not change JWT claims, cookie/CSRF semantics, route names, response shapes, event names, frontend code, WebDAV Basic Auth, upload scanning, cloud providers, persistence, encryption, backup/trash lifecycle, or product behavior. Do not introduce a new message protocol or reconnect policy.

### Prerequisite tests already present

- `test/auth-security.test.js`: permission removal, deletion/recreation, expiry, and real active-WebSocket revocation.
- `test/auth-core-boundaries.test.js`: claim and cookie parsing boundaries.
- `test/realtime-transport-boundaries.test.js`: payload/compression/binary/burst configuration and cookie/Origin/message boundaries.
- `docs/security/phase-2-2-closure-audit.md` and `docs/security/browser-session-threat-model.md`: source-backed transport and freshness invariants.

### Missing tests required before moving code

Add focused tests that fail if the extraction changes: rejected upgrade before `connected`, exact first-event ordering, stale/expired send rejection, heartbeat and idle termination, buffered-client close, message-rate reset, exact event envelope, and cleanup of the heartbeat timer on server close. Keep them in disposable fixtures and avoid real credentials or runtime data.

### Acceptance criteria for the future extraction PR

1. Only the transport boundary moves; the working-tree diff contains no unrelated route, persistence, provider, frontend, or product changes.
2. Existing realtime/auth tests and the new contract tests pass at the exact base and extracted head.
3. Browser WebSocket URLs remain credential-free and Origin/session freshness checks remain active.
4. Existing event names, payloads, response shapes, and producer call sites remain unchanged.
5. No new runtime artifacts, credentials, tokens, databases, uploads, or backups are created in the repository.
6. The PR documents the unchanged limitation that login JSON still contains an unused token.

### Rollback and reversibility

Keep the initial module as a thin adapter with no persistence migration. A single revert can restore the three inline blocks in `server.js`; no data, route, event, or provider state needs migration. Do not delete the old behavior until the extracted head has passed the focused and exact-head CI checks.

### Why safer than the next two alternatives

Realtime has the smallest state surface and the strongest direct security regression evidence, and it does not move file bytes or metadata. Upload scanning touches simple, chunked, and WebDAV entrypoints, quarantine files, pending state, and an unavailable live ClamAV dependency; cloud storage touches every file lifecycle plus two external provider modes and lacks external operational proof. Both alternatives therefore have larger coupling, more persistence/storage modes, and more direct D-009 conflict.
