# Root.ark Security Status

Root.ark has completed several bounded security-stabilization phases covering authentication configuration, browser rendering, session handling, WebSocket authentication, dependency validation, upload and archive boundaries, backup recovery, trash behavior, and runtime-artifact isolation.

This public document intentionally does not retain exploit-ready reproduction steps, obsolete vulnerable snippets, private paths, or a chronological dump of every historical finding. Detailed evidence belongs in focused pull requests, tests, and private vulnerability reports when disclosure would increase risk without helping users operate the project safely.

## Current position

- The latest reconciled application-code snapshot is `Root/main` SHA `8771d87084e458202d77ab956e3d341c0fe4868f`, after PRs #141 and #142. Exact-SHA Security Regression, CodeQL, Dependency Review, and Pages passed; closure remains partial while the official local release-gate result, quarantine-ingestion browser proof, and final post-documentation-SHA review remain outstanding. See [the current validation snapshot](../validation/2026-10-09-rootark-current-state.md).
- Root.ark is still under active development and is not production-ready.
- The default expectation is a private, administrator-controlled deployment on a trusted network.
- A strong explicit `JWT_SECRET` is required; no public fallback secret should be used.
- Browser authentication uses server-controlled session boundaries rather than persistent browser bearer-token storage.
- User-controlled text must be rendered as text, not injected as HTML.
- WebSocket authentication must not place credentials in URLs and must preserve session freshness checks.
- Local data, databases, backups, uploads, credentials, keys, and environment files must remain outside Git.
- Optional scanning, cloud, WebDAV, backup, and synchronization behavior still depends on deployment-specific validation.
- The approved future zero-knowledge product direction is not equivalent to the current implementation and requires separate architecture and migration work.

## Proxy and client-IP trust

Express proxy trust is disabled unless `TRUSTED_PROXIES` lists explicit proxy IP addresses or CIDR ranges. Client-IP derivation, rate limits, security audit identity, WebSocket origin checks, and origin-sensitive share mutations therefore use forwarded values only through the configured trusted-peer chain; caller-supplied forwarding headers from an untrusted direct peer are ignored. Configure each actual proxy hop and restrict origin ingress so direct callers cannot bypass the trusted proxy. Cloudflare requires the deployment-specific source-range and header-replacement controls described in the [browser session threat model](browser-session-threat-model.md). Repository checks do not establish the live network topology.

Production rejects persisted default development bootstrap credentials at startup. Login and WebDAV Basic authentication share the same process-local per-IP and per-username attempt state. WebSocket Origin and session checks run before upgrade; direct connections use the immediate TCP peer for upgrade budgets, while configured trusted-proxy chains use the nearest untrusted client address. These budgets are process-local, so multi-instance deployments need a shared upstream limit. Secure session cookies are required by readiness and cannot be disabled in production.

## Cloud file lifecycle boundary

Whole restore is a locally rollback-recoverable transaction, not an atomic switch visible across every storage domain. The supported app deployment has one server process per runtime: login/TOTP limits, login challenges, and TOTP replay state are process-local, so `server.js` rejects a declared `ROOTARK_RESTORE_INSTANCE_COUNT` other than `1` before acquiring restore leases or reading restore state. This is a declared-topology guard, not process discovery; deployment configuration must prevent hidden replicas. Multi-instance restore acknowledgements remain service-level recovery machinery and do not indicate supported multi-process authentication. Before mutation, it persists a coordinator and verified pre-images for the quarantine state, restorable data files, uploads tree, SQLite files and sidecars, and restore-derived provider suppression. It applies quarantine, data, uploads, SQLite, and backup metadata changes in sequence. If the process stops after the prepared boundary, startup verifies and restores the local pre-images in reverse order; a missing or corrupt recovery record keeps the service blocked for manual recovery. In the supported single-process deployment, successful restore remains behind a request barrier until the server migrates the restored database and binds its listener. The retained service-level multi-instance acknowledgement protocol is not a supported application topology while auth state is process-local. These guarantees cover the locally controlled runtime under tested process interruptions; they do not make the staged changes simultaneously visible or claim portable power-loss atomicity.

When restoring a backup with cloud storage enabled, restore requires a complete provider inventory before local mutation. Provider objects not certified by the selected archive are recorded in durable `data/.rootark-restore-provider-orphans.json` policy; `.rootark-restore-provider-orphans-state.json` distinguishes an initialized empty policy from a lost policy. If either file is missing or invalid, affected access and startup fail closed. Both files participate in local rollback and are excluded from backup archives. A local-only restore leaves inventory `unknown` with the selected backup ID; the cloud-disabled local service can remain available. Before cloud-enabled startup opens the listener or trusts provider inventory, it validates a selected archive with `cloud_complete: true`, then reconciles current local upload bytes. An incomplete or missing baseline remains blocked with instructions to select a complete backup through `ROOTARK_PROVIDER_INVENTORY_BASELINE_BACKUP_ID`. Startup waits for persisted lease/backoff deadlines and resumes due entries; retry delay is capped at one hour. If a provider attempt still fails, startup exits fail-closed with the queue intact for the next start. Markerless legacy inventory state requires explicit `ROOTARK_PROVIDER_INVENTORY_BASELINE_BACKUP_ID`; no latest-backup guess is made. On Windows, suppression is cleared only after fresh inventory confirms there are no case-colliding aliases. Ordinary reads/edits, historical-version bytes, bearer open-token redemption, WebDAV, and public-share delivery deny suppressed objects. Restore does not delete provider objects; an external writer may create objects after inventory. Cloud-provider state remains outside local pre-image rollback, and no distributed atomicity is promised.

Legacy pending restore coordinators do not record whether a provider inventory was captured, and an empty legacy reconciliation list is ambiguous. Startup requires the suppression policy for those coordinators and blocks if it is missing. Markerless legacy inventory also needs an explicit baseline backup ID via `ROOTARK_PROVIDER_INVENTORY_BASELINE_BACKUP_ID`; silently creating an empty policy or guessing a baseline could expose unarchived cloud objects. Verify the deployed provider topology and selected archive before operator-led recovery.

Restore-sync queues are also bound to a hashed provider namespace and authenticated principal. If startup finds a nonterminal queue with a missing or changed provider context while the saved inventory marker otherwise appears known, it validates the queue's archived baseline and rebuilds one unambiguous legacy queue before upload. A replacement queue durably records the queue it supersedes and retires it after any active lease ends; startup resumes that retirement after interruption. If more than one queue requires rebinding, the service fails closed with `LEGACY_RESTORE_SYNC_AMBIGUOUS`. Missing, incomplete, or unavailable baselines block provider access; no latest-backup guess or arbitrary queue selection is made. These controls are covered with disposable fixtures and fresh-process restart tests; live provider interoperability remains unverified.

Cloud-backed API rename and move currently fail closed with `503`. Their source deletion and destination upload do not yet have the durable relocation journal needed to recover safely from partial provider failure or process interruption; local-only rename and move remain available. This restriction is separate from WebDAV, which has its own relocation journal and recovery state machine.

Cloud cache hydration, file trash operations, folder trash restore/delete/retention cleanup, and temporary file/folder expiry cleanup coordinate with hashed exclusive-create lock files under the runtime `data/.rootark-cloud-file-locks` directory. Folder trash operations use the stable folder ID so restore, single delete, empty-trash, retention cleanup, and moving an active folder to trash serialize across application instances. File lifecycle work also acquires its parent folder lock, preventing a download/cache publication from recreating a folder while that folder is moved or deleted. Cross-folder moves acquire both folder locks in sorted order before the source file lock. Expiry cleanup rechecks current metadata under the lock and waits for provider deletion before removing a file's expiration record; provider failure leaves that record for a later cleanup retry. This intentionally serializes lifecycle work within one folder; unrelated folders proceed independently. Every application instance using the same files must share a filesystem that provides reliable exclusive-create semantics. Lock waits are bounded and fail closed. A lock is automatically reclaimed only when its recorded hostname matches the current host and the recorded PID is conclusively absent (`ESRCH`); this assumes the instances share the same host PID namespace. Live/permission-denied owners and unknown or remote hosts remain fail-closed. A process crash after creating a `<lock>.reaper` marker but before releasing it can strand that marker, causing later attempts to time out rather than reclaim the associated dead lock. For recovery, stop every process using the runtime, verify that both the lock and reaper records identify dead processes on the same host, and remove only that exact stale `.reaper` marker; the normal lock path can then reclaim the dead `.lock`. If either record is missing, corrupt, or names an unknown/remote host, keep the service fail-closed and use a verified backup or administrator-led recovery. Never delete a live marker or clear the lock directory wholesale. Regression coverage in `test/file-lifecycle-lock.test.js` exercises this interrupted-reaper boundary with disposable files.
The WebDAV stale-claim takeover also rechecks lock bytes and file identity before moving the claim, then verifies the moved evidence before granting a new owner. A disposable same-inode replacement injected at the rename boundary left the operation pending and caused no second provider upload. This is fail-closed against provider mutation, not availability: ambiguous takeover evidence can strand reconciliation until an operator verifies the local journal directory. A process with write access under the service identity remains inside the trusted local-host boundary. Regression: `same-inode lock replacement at stale takeover rename fails closed before provider retry` in `test/realtime-webdav-crash-consistency.test.js`.

Cloud temporary uploads use durable desired-state records in runtime `data/.rootark-cloud-temp-mutations`. Each record identifies one folder/name and records whether its provider object should be present or absent. The record is atomically persisted before provider reconciliation; upload and delete retries are idempotent, and startup plus a periodic worker resume pending records. Startup only synthesizes a legacy `present` intent when no durable intent exists, so an `absent` tombstone is not overwritten. Approval/rejection waits for temporary-object deletion; provider failure leaves the durable delete intent and returns HTTP `202` with `cloudCleanupPending: true`, while later retry/restart reconciles it.

Approved file contents and stored versions use durable desired-state records in runtime `data/.rootark-cloud-upload-mutations`. Approval persists the current and retained version upload intents before promoting pending bytes into `uploads/`; if queue persistence fails, local promotion does not begin. Version restore stages every retained upload intent before changing local bytes or history and rolls the intents back if local restore fails. Provider outages leave the intent for startup and periodic retry, and approval returns HTTP `202` with `cloudSyncPending: true` until cloud work completes. Successful upload reconciliation clears the matching restore-orphan suppression only after the provider accepted the selected local bytes. Other existing version-sync paths also use this queue. Provider I/O cannot be committed atomically with local filesystem or metadata writes. The queue and lock primitives can coordinate cooperating processes that share a filesystem with reliable create/rename semantics, but the application currently rejects a declared multi-process server topology because authentication state is process-local. Separate local directories never coordinate provider mutations. Unknown/remote-host stale locks require operator recovery as described above.

Hashed lock/queue control-file names come from internal IDs, and upload staging paths are generated under fixed runtime roots; HTTP callers cannot select either path. Uploaded bytes remain user-controlled content. `services/fileReadHandle.js` opens and pins descriptors before checking path identity, rejects symlinks where the platform supports no-follow opens, and bounds reads of WebDAV journals and claim/evidence files to 1 MiB and 64 KiB respectively. WebDAV metadata snapshots are bounded to 16 MiB per file on both persistence and recovery, leaving room for large metadata indexes while limiting any one recovery allocation. A regular file replaced before the first open cannot be distinguished without a trusted expected identity; parsed journal schemas and runtime-directory permissions remain part of the boundary. Node.js does not provide one portable no-follow/open-and-replace primitive with identical behavior on Windows and POSIX. A local process able to write as the Root.ark service identity can still race a lock/queue file, staged upload path, or read-handle path check. This is a bounded local-host residual, not a claim of protection against a process with the service account's filesystem access. Run Root.ark under a dedicated OS identity, keep `data/`, `uploads/`, and `temp/` writable only by that identity, and do not run untrusted local processes under it or share those writable directories with other tenants. On Windows, enforce the equivalent restrictions with NTFS ACLs; POSIX mode bits alone are not an adequate deployment policy for every platform. Regression coverage includes `bounded reader accepts regular files within the limit and rejects oversized files`, `bounded reader rejects symlinks where supported`, `oversized WebDAV MOVE journal fails closed before startup recovery`, and `oversized WebDAV MOVE metadata snapshot fails closed before checksum verification`.

Legacy public-link `maxViews` and `maxDownloads` counters are reserved in an immediate SQLite transaction when `DB_ENABLED=true`, so application processes using the same SQLite database serialize each quota check and update. A JSON-fallback link is inserted into SQLite in that same quota transaction, and recorded/revoked SQLite tokens suppress stale JSON copies. This cannot infer a removal made by an older version that left a stale JSON copy but no SQLite tombstone; reconcile `public-links.json` before explicitly enabling `DB_READ_FALLBACK_JSON=true` on an existing database. After a token is recorded or revoked in SQLite, stale JSON cannot reactivate it. JSON persistence remains supported for single-process deployments, but its file-backed counter writes do not coordinate between processes; do not use JSON mode for multi-process share quotas. Separate SQLite databases also do not share counters. These use limits do not turn bearer links into operation-scoped capabilities or make them Zero-Knowledge; Issue #68 remains open.

Public-share viewer cookies are accepted only when the ID matches the generated 32-character lowercase-hex form and maps to an own active-viewer entry. Preview bytes consume one `maxDownloads` unit per active viewer session, including valid HTTP Range fragments, so browser PDF/media readers do not exhaust the allowance while loading one preview. Explicit POST file/download requests still count per request. HEAD, unsupported preview types, unsatisfiable ranges on preview and POST delivery, and requests denied before stream headers are written do not reserve a download. Direct preview requests without an active viewer session count per request. After a preview loads, the share page refreshes the displayed allowance and disables Download when it reaches zero.

Expired file and folder records are denied at authorization and read boundaries even while local cached bytes still exist. Expired folders are omitted from navigation/search and rejected by folder-scoped routes. File listing, direct download, preview, encrypted download, version reads, WebDAV, open-token creation/redemption, and public-share resolution recheck expiration; asynchronous cache hydration is followed by another expiry check before content is returned. Expiry cleanup is asynchronous, so inaccessible bytes may remain on disk until cleanup completes. Disposable regression coverage is in `test/expired-content-access-security.test.js` and the cloud lifecycle security suite.

Trash-manager authority is refreshed after a single-item or empty-trash operation acquires its lifecycle lock. The current account, enabled state, session version, and normalized permissions are checked again before destructive work, and bulk deletion stops at the first failed recheck. This prevents a request that waited on a lifecycle lock from carrying stale manage-trash authority into the mutation; a permission change can still race after the in-lock recheck has already allowed an operation to begin.

Google Drive lookups, downloads, updates, single-object deletes, and folder-prefix deletes verify the canonical `rootArkKey`, matching folder/area metadata, and configured parent before using a file ID. Prefix deletion uses the same filtered inventory as listing and re-reads ownership metadata before each delete. These checks prevent serial requests from hydrating or deleting objects that merely claim the app's folder metadata. They cannot make a Drive read/check/update/delete sequence atomic against an external actor changing the provider object between API requests; the current Drive v3 adapter has no conditional version precondition for those operations. Keep the configured Drive parent and service-account credentials restricted to the Root.ark deployment. Google documents that the Drive v2 `Files.etag` field has no v3 equivalent in its [v2-to-v3 field mapping](https://developers.google.com/workspace/drive/api/guides/v2-to-v3-reference); do not treat the ownership check as protection against concurrent external provider writers.

## Public security guidance

Use [SECURITY.md](../../SECURITY.md) to report vulnerabilities responsibly. Do not open public issues containing working exploits, real credentials, private paths, personal data, or sensitive deployment details.

## Evidence and regression coverage

Security changes should be backed by focused automated tests, exact-revision validation, disposable data, dependency review, and a clean-checkout artifact check. Historical pull requests and the repository test suite remain the authoritative public evidence for merged remediation work.

## Remaining responsibility

A passing test suite does not make an arbitrary deployment safe. Operators are responsible for network exposure, reverse-proxy configuration, TLS, secret management, operating-system permissions, enabled providers, backup handling, and the exact revision deployed.

Dynamic HTTP requests pass through a per-trusted-client-IP API ceiling before body parsing, in addition to route-specific limits such as `/upload-chunk` before Multer staging. The in-memory stores are per process; deployments with multiple workers need a shared rate-limit store for a deployment-wide budget. `API_RATE_LIMIT_MAX` defaults to ten times `ROUTE_RATE_LIMIT_MAX` and shares its time window. Cloud-backed file and version token creation is limited before a provider cache miss. The local chunk-upload limit reduces repeated staging requests per process but does not close Issue #94, which remains open for deployment-wide enforcement across multiple processes or replicas.
