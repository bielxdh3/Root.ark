# Root.ark Security Status

Root.ark has completed several bounded security-stabilization phases covering authentication configuration, browser rendering, session handling, WebSocket authentication, dependency validation, upload and archive boundaries, backup recovery, trash behavior, and runtime-artifact isolation.

This public document intentionally does not retain exploit-ready reproduction steps, obsolete vulnerable snippets, private paths, or a chronological dump of every historical finding. Detailed evidence belongs in focused pull requests, tests, and private vulnerability reports when disclosure would increase risk without helping users operate the project safely.

## Current position

- Root.ark is still under active development and is not production-ready.
- The default expectation is a private, administrator-controlled deployment on a trusted network.
- A strong explicit `JWT_SECRET` is required; no public fallback secret should be used.
- Browser authentication uses server-controlled session boundaries rather than persistent browser bearer-token storage.
- User-controlled text must be rendered as text, not injected as HTML.
- WebSocket authentication must not place credentials in URLs and must preserve session freshness checks.
- Local data, databases, backups, uploads, credentials, keys, and environment files must remain outside Git.
- Optional scanning, cloud, WebDAV, backup, and synchronization behavior still depends on deployment-specific validation.
- The approved future zero-knowledge product direction is not equivalent to the current implementation and requires separate architecture and migration work.

## Cloud file lifecycle boundary

Whole restore is a locally rollback-recoverable transaction, not an atomic switch visible across every storage domain. Before mutation, it persists a coordinator and verified pre-images for the quarantine state, restorable data files, uploads tree, SQLite files and sidecars, and restore-derived provider suppression. It applies quarantine, data, uploads, SQLite, and backup metadata changes in sequence. If the process stops after the prepared boundary, startup verifies and restores the local pre-images in reverse order; a missing or corrupt recovery record keeps the service blocked for manual recovery. Successful restore remains behind a request barrier until each configured instance has migrated the restored database, bound its listener, and acknowledged the restore. These guarantees cover the locally controlled runtime under tested process interruptions; they do not make the staged changes simultaneously visible or claim portable power-loss atomicity.

When restoring a backup with cloud storage enabled, the restore now requires a complete provider inventory before local mutation. Provider objects not certified by the selected archive are recorded in the durable `data/.rootark-restore-provider-orphans.json` policy, which participates in local rollback and is excluded from future backup archives. An archive with `cloud_complete: false` cannot certify that same-name provider objects contain its selected bytes, so those objects stay suppressed while every selected `uploads/` entry is durably queued for reconciliation. After the local restore restart barrier clears, reconciliation uploads the selected local bytes and clears that entry only after provider success. Provider failures remain durably retryable with exponential backoff capped at one hour; stale objects stay inaccessible until the selected bytes are accepted. Ordinary file reads/edits, historical-version bytes, bearer open-token redemption, WebDAV, and public-share delivery deny suppressed objects; authorized access managers can review or clean them up. Restore does not delete provider objects, and an external provider writer can still create a new object after inventory; provider state is not part of the portable local rollback transaction.

Cloud-backed API rename and move currently fail closed with `503`. Their source deletion and destination upload do not yet have the durable relocation journal needed to recover safely from partial provider failure or process interruption; local-only rename and move remain available. This restriction is separate from WebDAV, which has its own relocation journal and recovery state machine.

Cloud cache hydration, file trash operations, folder trash restore/delete/retention cleanup, and temporary file/folder expiry cleanup coordinate with hashed exclusive-create lock files under the runtime `data/.rootark-cloud-file-locks` directory. Folder trash operations use the stable folder ID so restore, single delete, empty-trash, retention cleanup, and moving an active folder to trash serialize across application instances. File lifecycle work also acquires its parent folder lock, preventing a download/cache publication from recreating a folder while that folder is moved or deleted. Cross-folder moves acquire both folder locks in sorted order before the source file lock. Expiry cleanup rechecks current metadata under the lock and waits for provider deletion before removing a file's expiration record; provider failure leaves that record for a later cleanup retry. This intentionally serializes lifecycle work within one folder; unrelated folders proceed independently. Every application instance using the same files must share a filesystem that provides reliable exclusive-create semantics. Lock waits are bounded and fail closed. A lock is automatically reclaimed only when its recorded hostname matches the current host and the recorded PID is conclusively absent (`ESRCH`); this assumes the instances share the same host PID namespace. Live/permission-denied owners and unknown or remote hosts remain fail-closed. If a lock cannot be reclaimed, stop every instance sharing the runtime, verify that no protected operation is active, and remove only the specific confirmed-stale lock file. Do not clear the lock directory wholesale.

Cloud temporary uploads use durable desired-state records in runtime `data/.rootark-cloud-temp-mutations`. Each record identifies one folder/name and records whether its provider object should be present or absent. The record is atomically persisted before provider reconciliation; upload and delete retries are idempotent, and startup plus a periodic worker resume pending records. Startup only synthesizes a legacy `present` intent when no durable intent exists, so an `absent` tombstone is not overwritten. Approval/rejection waits for temporary-object deletion; provider failure leaves the durable delete intent and returns HTTP `202` with `cloudCleanupPending: true`, while later retry/restart reconciles it.

Approved file contents and stored versions use durable desired-state records in runtime `data/.rootark-cloud-upload-mutations`. Approval persists the current and retained version upload intents before promoting pending bytes into `uploads/`; if queue persistence fails, local promotion does not begin. Version restore stages every retained upload intent before changing local bytes or history and rolls the intents back if local restore fails. Provider outages leave the intent for startup and periodic retry, and approval returns HTTP `202` with `cloudSyncPending: true` until cloud work completes. Successful upload reconciliation clears the matching restore-orphan suppression only after the provider accepted the selected local bytes. Other existing version-sync paths also use this queue. Provider I/O cannot be committed atomically with local filesystem or metadata writes. Multi-instance deployments must share both queue directories and the lock filesystem with reliable create/rename semantics; separate local directories do not coordinate provider mutations. Unknown/remote-host stale locks require operator recovery as described above.

Hashed lock/queue control-file names come from internal IDs, and upload staging paths are generated under fixed runtime roots; HTTP callers cannot select either path. Uploaded bytes remain user-controlled content. Node.js does not provide one portable no-follow/open-and-replace primitive with identical behavior on Windows and POSIX; a local process able to write as the Root.ark service identity can still race a lock/queue file or staged upload path. This is a bounded local-host residual, not a claim of protection against a process with the service account's filesystem access. Run Root.ark under a dedicated OS identity, keep `data/`, `uploads/`, and `temp/` writable only by that identity, and do not run untrusted local processes under it or share those writable directories with other tenants. On Windows, enforce the equivalent restrictions with NTFS ACLs; POSIX mode bits alone are not an adequate deployment policy for every platform.

Expired file and folder records are denied at authorization and read boundaries even while local cached bytes still exist. Expired folders are omitted from navigation/search and rejected by folder-scoped routes. File listing, direct download, preview, encrypted download, version reads, WebDAV, open-token creation/redemption, and public-share resolution recheck expiration; asynchronous cache hydration is followed by another expiry check before content is returned. Expiry cleanup is asynchronous, so inaccessible bytes may remain on disk until cleanup completes. Disposable regression coverage is in `test/expired-content-access-security.test.js` and the cloud lifecycle security suite.

Trash-manager authority is refreshed after a single-item or empty-trash operation acquires its lifecycle lock. The current account, enabled state, session version, and normalized permissions are checked again before destructive work, and bulk deletion stops at the first failed recheck. This prevents a request that waited on a lifecycle lock from carrying stale manage-trash authority into the mutation; a permission change can still race after the in-lock recheck has already allowed an operation to begin.

Google Drive lookups, downloads, updates, single-object deletes, and folder-prefix deletes verify the canonical `rootArkKey`, matching folder/area metadata, and configured parent before using a file ID. Prefix deletion uses the same filtered inventory as listing and re-reads ownership metadata before each delete. These checks prevent serial requests from hydrating or deleting objects that merely claim the app's folder metadata. They cannot make a Drive read/check/update/delete sequence atomic against an external actor changing the provider object between API requests; the current Drive v3 adapter has no conditional version precondition for those operations. Keep the configured Drive parent and service-account credentials restricted to the Root.ark deployment. Google documents that the Drive v2 `Files.etag` field has no v3 equivalent in its [v2-to-v3 field mapping](https://developers.google.com/workspace/drive/api/guides/v2-to-v3-reference); do not treat the ownership check as protection against concurrent external provider writers.

## Public security guidance

Use [SECURITY.md](../../SECURITY.md) to report vulnerabilities responsibly. Do not open public issues containing working exploits, real credentials, private paths, personal data, or sensitive deployment details.

## Evidence and regression coverage

Security changes should be backed by focused automated tests, exact-revision validation, disposable data, dependency review, and a clean-checkout artifact check. Historical pull requests and the repository test suite remain the authoritative public evidence for merged remediation work.

## Remaining responsibility

A passing test suite does not make an arbitrary deployment safe. Operators are responsible for network exposure, reverse-proxy configuration, TLS, secret management, operating-system permissions, enabled providers, backup handling, and the exact revision deployed.

The route-scoped HTTP request limits and cloud-cache-miss account budgets use per-process in-memory stores. Each process or container enforces its own budget; deployments with multiple workers need a shared rate-limit store for a deployment-wide budget. Cloud-backed file and version token creation is limited before a provider cache miss. This does not close Issue #94: the separate multi-process `/upload-chunk` gate remains open.
