# Root.ark issue #65 — signed exact operation and real PostgreSQL ciphertext readback

## Bounded standalone milestone

This experiment joins **three existing security boundaries**: (1) the PostgreSQL physical chunk-writer and transactional gate, (2) its independently checked `SEALED` row and full ordered ciphertext chunks, and (3) the local Ed25519-signed complete version inventory, where an entry binds the exact 16-byte `operation_id`, scope, revision, epoch, ciphertext SHA-256 and expected predecessor root.

It does **not** integrate a production protected-file API, prove external/cloud-provider durability, ensure multi-host independent administration or provide an authorization to decrypt/serve ciphertext. Production release remains **NO-GO**.

### What is physically checked before signing

- `Zk1SharedPgCiphertextSink.putSealed` uses the existing PostgreSQL gate; its chunk INSERT and seal check are ordered by the authoritative PostgreSQL head/generation lock. The writer finishes its admission before this bridge advances the inventory.
- Before its first chunk, `Zk1SharedPgPhysicalInventoryIntent.reserveExact` persists an immutable PostgreSQL `physical_inventory_intent` using a separately preflighted gate-operator login. The table locks the exact OPEN generation and binds **operation ID**, fixed inventory predecessor sequence/root, account/compartment/keyring, revision, epoch, trusted request digest, ciphertext SHA-256, physical chunk root and count. A BEFORE INSERT trigger forbids binding an already written/unbound object; UPDATE/DELETE triggers reject mutation. Concurrent conflicting owners cannot relabel existing physical ciphertext. An intent alone is never a signed success.
- **New opt-in strict physical-intent scopes:** an immutable `head.require_physical_inventory_intent=TRUE` is set only during trusted initial provisioning. PostgreSQL rejects the first strict PUT admission before an exact prewrite intent exists. Its AFTER INSERT trigger, within the same head-locked transaction, records an immutable, first-writer-wins `physical_inventory_admission` tuple associating scope/object/generation, exact operation ID and exact admission ID. Restricted gate/child INSERT cannot append unreserved/out-of-range chunks; the `SEALED` trigger enforces intent root/count/generation and this exact admission, setting `sealed_object.operation_id` from PostgreSQL's immutable prewrite reservation (not from the caller). A concurrent second admission is rejected, not used to relabel a different worker's physical effect. Existing scopes remain non-strict to avoid claiming retrofit coverage; the attestor rejects their physical inventory proof. The strictly bound admission can still be minted by a trusted/compromised gate operator after prewrite reservation: **this is not owner/device authorization.**
- **Early migration-mode fail-closed gate:** `Zk1SharedPgPhysicalInventoryIntent.reserveExact` now requires `require_physical_inventory_intent=TRUE` on its locked PostgreSQL head **before** creating any immutable prewrite intent. Previously the bridge could reserve/write a legacy non-strict scope only to have its read-only attestor reject the scope after the physical effect. A real PG18 negative test now provisions a legacy scope and verifies refusal before any admission, intent, chunks, SEALED row or Ed25519 inventory append. This is a non-production safety improvement, not a migration of historical legacy scopes.
- The **new** `zk1_physical_attestor_runtime` (NOLOGIN, NOINHERIT) is provisioned separately from gate, STOP and chunk-writer roles. A dedicated test-only login gets only SELECT on the physical proof tables and the bounded WAL barrier. The attestor preflight refuses superuser, DDL, replication/BYPASSRLS, schema CREATE, per-column/table INSERT/UPDATE and MAINTAIN on **all** protected gate/STOP/writer/physical tables, destructive DELETE/TRUNCATE and REFERENCES/TRIGGER capabilities. It scans **all reachable PostgreSQL role memberships** (even NOINHERIT/SET ROLE) and rejects any predefined `pg_*` role such as `pg_execute_server_program` or `pg_write_server_files`, which can grant OS-level powers without ordinary table DML. Direct and dormant grants are checked instead of trusting current-role effective permissions alone. This is separate SQL privilege custody; it is not separate ownership of the PostgreSQL server, and its historical role preflight cannot prevent a separately trusted database administrator from changing the ACLs later.
- `Zk1SharedPgPhysicalCiphertextVerifier` opens its own `REPEATABLE READ READ ONLY` PostgreSQL transaction, refuses `fsync != on`, `synchronous_commit != on` or `full_page_writes != on`, and independently checks the sealed object's scope/keyring, revision, gate head generation/digest/phase, persisted admission ID and chunk count. It rereads all ordered ciphertext bytes and recomputes both the versioned length/index-aware chunk root and SHA-256 over the exact ciphertext stream, from a caller-supplied trusted object commitment. Its positive result is not a cryptographically signed remote-provider receipt.
- A separately granted `SECURITY DEFINER` SQL WAL barrier runs **after** independent physical reread and waits at most two seconds for `pg_current_wal_flush_lsn() >= pg_current_wal_insert_lsn()`. This closes a concrete gap in merely checking `SHOW synchronous_commit` in the reader: the original writer could have used `SET LOCAL synchronous_commit=off`. The function leaks no WAL value and is not a general SQL broker. A failed/denied or timed-out barrier means **no signed inventory publication**. The role also rejects old column-level INSERT/UPDATE privilege grants, not merely table-level privileges.
- `Zk1PgPhysicalInventoryBridge` detaches all request bytes and validates owner-supplied SHA-256/root **before physical IO**, then calls the existing physical sink. It demands separately verified physical readback before any local Ed25519 inventory append; afterwards, it re-reads the physical ciphertext and independently verifies the exact signed operation receipt. An alleged `SEALED` HTTP/adapter acknowledgment alone can never mint a signed inventory entry.
- The bridge explicitly rejects a physical input scope different from its fixed Ed25519 ledger scope **before** any PostgreSQL reservation, ciphertext write or SQLite append. This closes an independently found cross-scope signed-ledger contamination path; post-write scope checking would be too late.
- **Optional owner-pinned rollback floor in the physical bridge:** when a separate trusted client supplies a previously verified signed `minimumSnapshot` and matching `{sequence,root}` before construction, `Zk1PgPhysicalInventoryBridge` copies both immutably and verifies a fresh Ed25519 snapshot and the exact complete sequence of signed intermediary operations (at most 64) before any new physical intent/write or inventory append. It also checks the signed catalog contains the physically reconciled tuple. Divergent roots, future floor, altered/reordered/missing receipts or changed catalog head reject closed, retaining existing bytes and prior signatures. This is effective against SQLite-only rollback **relative to an actually independently retained floor**; the bridge does not invent, store or synchronize that floor and does not prove a separately administered anchoring service.
- **New optional physically gated mTLS inventory append:** the standalone `/v1/inventory/append` endpoint may be constructed with an actual `Zk1SharedPgPhysicalCiphertextVerifier` instance. For this explicit experimental mode, mTLS append identity alone is not enough: the verifier obtains exact prewrite commitment fields from the restricted physical-intent database by independently matching the scope, keyring, object, `operation_id`, predecessor inventory sequence/root, revision/epoch and ciphertext SHA-256. It then independently verifies the SEALED admission, physical ciphertext root, SHA-256, generation and local WAL flush **before** any local SQLite signed inventory append. After the append, it rechecks the physical ciphertext before returning positive HTTP success. Legacy standalone deployments without this explicit verifier remain nonauthorizing signed-ledger transports; enabling the opt-in verifier does **not** retrofit or close those other call paths.
- The optional physical mTLS path bounds CPU, PostgreSQL pool and memory amplification by rejecting simultaneous append/status proof work under the same certificate, capping physical-mode append/status **attempts** at **two concurrent per service**, **four accepted attempts per certificate per 60 seconds** and **16 accepted attempts globally per 60 seconds**, measured with a monotonic clock. Even unknown/pending status lookups count toward the budget because an uncommitted ID can still cause a full SQLite catalog read; malformed or corrupted append evidence also consumes a budget slot after validation. Snapshot and chain requests do not use this physical-mode budget. Excess requests receive 503 without a new signed inventory operation. The remaining two active verifications are bounded by PostgreSQL statement deadlines; disconnect is not a cryptographic rollback of a verification already in progress.
- **Committed status reconciliation in physical mTLS mode:** `/v1/inventory/operation` now performs the same live independent PostgreSQL readback, immutable intent/admission and WAL proof before reporting `committed`. A signed historical operation with modified bytes or a closed gate receives a fail-closed 503, while the ledger receipt remains preserved as history. All status lookups share the append attempt limits (two active, four per client certificate and sixteen global per minute); `unknown`, `pending`, snapshot and chain remain historical information. Without the explicitly configured physical verifier, operation status remains a signed-ledger-only report. Neither mode grants protected GET/release authority, external durability or monotonic rollback immunity.
- Replay/restart reconciliation never reissues a write admission if the exact signed operation already exists. A lost physical readback reply after `SEALED` leaves signed status `unknown` and physical bytes intact. A later operator-side `publishExisting` may recover the signed catalog only after successful fresh physical readback. Gate generation advance, partial upload or ciphertext mutation makes a previously signed historical receipt nonauthorizing.

### Adversarial and crash boundaries

- Fresh physical bytes and signed operation matching over real PostgreSQL + SQLite; retry without a second PUT; SQLite restart recovery.
- Outage after genuine committed `SEALED`, before signed inventory publish; recovery from separately verified storage rather than trusting the lost acknowledgment.
- Partially inserted bytes without sealed marker; never sign or reclaim this as complete.
- Incorrect owner-authenticated hash blocks I/O before admitting a worker.
- Gate transition to QUIESCING/PENDING (stale generation) denies fresh physical verification regardless of surviving signed historical inventory.
- Privileged PostgreSQL administrator mutating ciphertext after signing causes physical revalidation failure.
- Read-only attestor login cannot insert/delete chunks or update gate head, and runtime gate identity cannot impersonate the attestor.
- Per-column `INSERT` granted to a poisoned attestor login is rejected even when table-level INSERT remains false.
- Physical SEALED revision can never be bound to a second operation ID, and a foreign scope cannot cause the local ledger to sign a false entry.
- A PostgreSQL transaction with `SET LOCAL synchronous_commit=off` is followed by a successful independently operated WAL flush barrier, before the verifier may return.
- Strict prewrite intent, atomic admission-ID second-phase binding, immutable binding tamper rejection, second-admission rejection, direct SQL chunk bounds and physical sealed operation-ID tamper/reconcile failures pass against real PostgreSQL 18. Deliberately poisoned attestor logins with `TRUNCATE` over physical intent and `DELETE` over sealed rows, `UPDATE(state)` over worker admissions, or `INSERT` columns on gate head are each rejected before physical readback, even though the ciphertext remains intact.
- A PostgreSQL 18 adversarial `SET ROLE` test demonstrates a real blind spot in the previous direct-grant check: a normal attestor login can set an unrelated `NOINHERIT` role granted `TRUNCATE` over physical intent while its original `current_user` has no destructive privilege. The initial security assertion failed **RED** (unexpected positive verification); scanning the reachable PostgreSQL role-membership graph fixed the bypass, then the disposable physical PostgreSQL suite passed **GREEN, 57/57** with verified owned cleanup. The positive isolated read-only login still passes all ordinary physical reread cases.
- Additional PostgreSQL 18 adversarial tests exercise `MAINTAIN` on a protected SEALED table, `CREATE` on the protected schema and indirect NOINHERIT/SET ROLE access to `pg_execute_server_program`. The latter asserts reachable OS command privilege **without executing any OS command**. The privileged-role findings are P1-risk permissions on the attestor identity, not evidence of host execution in the fixture. Fail-closed preflight rejects all cases before physical reread.
- Existing physical-worker tests cover hard `SIGKILL` before a PostgreSQL COMMIT, cross-process HEAD locking and strict signed STOP; these are independent tests, **not** claims that the new bridge itself owns every worker socket.

## Deliberately unsolved

- **No cross-database atomic commit.** PostgreSQL may have durable sealed ciphertext while SQLite inventory is still unknown. The bridge fails closed and permits explicit later reconciliation, never deletes or overwrites the sealed ciphertext. Reverse inconsistency after hostile disk rollback remains possible and must be caught by external monotonic anchors and fresh physical checks.
- **Trusted floor is caller custody.** An optional pinned snapshot cannot prevent rollback when the client has lost that snapshot, when both copies are rolled back together, or when the compromised inventory signer forges a new history. Passing a floor derived from the same mutable SQLite file is NOT an independent rollback anchor. There is no automatically provisioned multi-provider authority.
- **No cross-database/physical-signed atomic commit for mTLS either.** The physically gated mTLS endpoint can commit an authentic historical Ed25519 inventory entry before its post-commit readback discovers an intervening physical corruption, at which point it responds 503. This preserves auditability, but cannot retract the signed historical event; the client must never use that receipt as a stand-alone GET/release authorization.
- **No protected-content authorization:** the bridge requires a trusted upstream owner/device authorization layer supplying the ciphertext root and exact request digest. It is not safe to expose directly to arbitrary web clients.
- **No independent device-vetted admission:** the second-phase physical admission pin is SQL-enforced first-writer-wins, but a compromised gate with permission to create valid admissions after a physical intent exists can deny service or claim a bound admission. The signed inventory still requires the separate verified bytes and operator-owned ledger key. This is not a capability-token or independent device authorization check.
- **No durable external attestation:** a PostgreSQL WAL acknowledgment with `fsync` and `synchronous_commit` enabled is stronger than an unverified application ACK, but not proof against an administrator with full control of PostgreSQL disks or against a malicious cloud storage provider.
- **Confirmed local WAL, not external durability:** the new barrier actually waits for WAL flush through the PostgreSQL primary after the signed operation-specific physical readback; this is local PostgreSQL crash-durability evidence, still not external replication, hostile disk rollback resistance or a third-party attestation. The durable prewrite binding persists only in the same PostgreSQL administrative domain and is not an independently hosted monotonic anchor.
- **No absolute I/O fencing after response:** physical PostgreSQL writes are gated in transactional SQL; the bridge checks the live generation and phase at verification time, not continuously for every future read or against SQL host takeover. No external provider's kernel sockets or remote cache is under this module's control.
- **Provider support:** only the existing PostgreSQL reference physical sink is integrated. Local filesystem, S3, GDrive, WebDAV, backup/restore, device enrollment/revocation and migration need their own verified sink/effect boundary and independent operational control.
- **Read-only cloud copy milestone (subsequent experimental delta):** an explicit `Zk1CloudCiphertextReadbackVerifier` now uses the existing S3 or Google Drive `createCloudStorage` **download-only** adapter under a separately pinned provider-reader identity digest to fetch an opaque, scope-and-exact-operation-addressed ciphertext copy into a disposable local directory. The provider streams are capped to the expected total size before hitting disk; a descriptor-pinned regular-file reread checks exact SHA-256, ordered domain-separated chunk root and chunk lengths, and validates the provider identity again after GET. `Zk1PgPhysicalInventoryBridge.reconcileCloudCopy` requires a preexisting physically sealed and signed operation in PostgreSQL, then the matched cloud readback, and repeats the signed/local PostgreSQL proof after cloud I/O. Tests exercise real disposable PostgreSQL with a fake S3 backend and existing S3/Google Drive adapters with restricted synthetic backends. This is a **non-authorizing point-in-time readback consistency result only**. It deliberately does not upload to cloud, provide independent cloud receipts, prove provider persistence/durability, bind the cloud provider's kernel I/O to physical STOP/quiescence, release GET to a user, or establish separate administrative ownership of credentials. Provider GET must use explicitly provisioned reader credentials; the module never takes a provider write credential by itself.
- **Cloud readback P2 review hardening:** all SQL proofs now consume one detached immutable operation snapshot. A deliberately malicious length-array Proxy cannot retarget two distinct legitimate signed operations between the initial PG proof and cloud GET. A bounded 15-second cancellation budget now applies to each external identity probe and the cloud GET, including the *pre-body* S3/Drive discovery/request step; streaming bytes are separately capped at the expected exact size. Bounded ZK-only downloads use atomic hard-link publication that fails if another file raced into the destination (rather than returning `true` for someone else's bytes). A descriptor-pinned read uses bigint file IDs, inode/size/mtime/links and SHA-256/chunk root, and refuses hardlinked unexpected local files. These controls prevent claiming a false copy from these specific races; they cannot force a hostile provider to retain bytes after readback.
