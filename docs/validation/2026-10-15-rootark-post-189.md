## Restore transaction and residual boundary

The restore implementation provides a durable local rollback/recovery protocol, not simultaneous atomic visibility across all domains. It prepares and verifies preimages for locally controlled data before mutation, then applies quarantine, filesystem/JSON state, uploads, SQLite and sidecars, provider policy/state, and backup/history metadata under a durable coordinator and request/startup gate. Startup recovery verifies and restores local preimages in reverse order after an interrupted prepared transaction. Migrations use forward retry after the restore commit boundary. Provider reconciliation is durably queued and retried idempotently after local recovery/commit; provider APIs cannot participate in the local filesystem/SQLite transaction.

PR #189 added a disposable child-process crash test that exits after the provider-orphan policy rename and before its state-file rename. On restart, recovery restores the prior pair before provider work and listener request handling resume. This proves that specific interruption boundary only. It does not prove that every restore stage has globally atomic visibility, that external cloud state can be rolled back, or that portable Windows directory-entry power-loss durability exists. A missing or corrupt rollback record remains fail-closed for operator recovery. Whole restore must not be described as fully atomic.
