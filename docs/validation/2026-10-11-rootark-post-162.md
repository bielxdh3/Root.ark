## Restore transaction model and residual boundary

Restore validates the selected backup, manifest, archive paths, quarantine input, provider inventory, and request quiescence before local mutation. It writes a durable coordinator and stages/validates preimages for every locally controlled destination the selected archive can change. After the `prepared` marker, the mutation order is quarantine, JSON/data files, uploads, SQLite replacement, provider-orphan policy, and backup-history metadata. A failure before local commit leaves a coordinator that blocks HTTP and WebSocket work; restart validates the preimage manifest and resumes reverse-order compensation before migrations or request handling. SQLite has its own staged replacement journal; quarantine has a separately recoverable journal. Migrations run after the local `restart_required` boundary and retry forward on later startup if one fails. The restore barrier remains until configured startup acknowledgements, local staging cleanup, and provider reconciliation complete.

The suite injects failures before local commit; after quarantine and upload/data stages; before and after SQLite replacement/commit; during migration and restart acknowledgement; before/after provider-policy and durable queue writes; on provider failure; and after interruption during rollback. Tests use disposable temporary state and fake providers. Provider retries preserve deterministic object identity and persisted retry state. External cloud APIs cannot join a local filesystem/SQLite transaction, and external writers that bypass Root.ark's gate can observe intermediate local changes. Node.js does not provide portable Windows directory-entry `fsync`; rollback can require operator-assisted recovery after missing/corrupt preimages, permission loss, or persistent storage failure. These bounds are documented in [the restore transaction boundary](../backup-restore-transaction-boundary.md). No claim of instantaneous cross-domain atomicity is made.
