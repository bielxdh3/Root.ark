# Root.ark #65 — offline ZK backup pre-restore fixture inspector

**Status:** non-authorizing disposable fixture milestone. **Production: NO-GO.**

## Existing trust boundary

The normal `src/routes/backups.js` endpoints authenticate and require backup access. The normal `POST /backups/:id/restore` delegates to `restoreService.restoreBackup` after application authorization and confirmation. The legacy backup is a ZIP with `backup-manifest.json`, `included_files`, local state files and optional uploads. `services/restoreService.js` validates archive membership, entry sizes and legacy restore boundaries, creates preimages and commits recovery state, with separate provider reconciliation. None of that is an independently trusted ZK authorization manifest, a client decryption proof, or a signed CAS/witness-backed monotonic recovery authority. Legacy backup metadata and archive checksums do not establish confidentiality, key recovery completeness or ZK restore eligibility.

The frozen `docs/architecture/zero-knowledge-migration-contract.md` section 10 requires owner-authorized inventory, per-version ciphertext and metadata integrity, a verified client recovery path, protected backup/trash/derived-copy reconciliation and explicit rollback/erasure policy. Normal backup ZIPs cannot safely be interpreted as that future schema. This milestone does **not** parse or extract ZIP archives or inspect existing backups.

## Implemented independent gate

`src/services/zk1DisposableBackupPreRestore.js` exports only `inspectZk1DisposableBackupPreRestore({ fixtureDir, expectedCompartmentId, checkpoint })`. It contains no route, writer, cloud adapter, deletion, restore call, plaintext decoder, secret/key import or application integration. Any output — even a fully valid fixture — sets `readOnly:true`, `restoreAuthorized:false`. `fixtureVerified:true` means **only** that the local synthetic structural/hash checks succeeded. The return includes fixed machine-readable finding codes and counts, never raw bytes, filenames, absolute paths, secrets or account identifiers.

The input must be a direct child directory of the OS temporary directory with a `rootark-zk-backup-fixture-` prefix and an exact sentinel `.rootark-disposable-fixture` containing `rootark-zk-backup-fixture-v1\n`. Exactly six root entries are accepted: the sentinel, `manifest.json`, `backup-index.json`, and `versions/`, `copies/`, `envelopes/`. A JSON manifest and independent local backup index use separate fixed **fixture-only** schemas. The index binds the raw canonical manifest with SHA-256 and enumerates all expected version IDs, backup-copy IDs and owner/recovery-envelope IDs. Each declared object requires a contiguous version chain from sequence 1, an exact parent version, a distinct backup copy for every version, a distinct owner/recovery envelope pair for every version, and a SHA-256 commitment for each ciphertext and opaque envelope. The declared sets must exactly match the directory entries. All payload hashes are calculated independently from disk.

Strict canonical JSON roundtrip rejects duplicate keys, trailing material and noncanonical representations. Fixed allowed fields reject unexpected metadata. Every ID is bounded to a safe single path component; root/ancestor, directory and file symlinks, unexpected filesystem entries, hard-linked files, missing references, oversized inputs and traversal are rejected. Reads use no-follow descriptors where supported and check inode, file length, link count and observed state before/after the read. A trusted, non-concurrent synthetic fixture is required: directory/name validation does not eliminate time-of-check/time-of-use attacks by a privileged concurrent writer. No part of this module should be called with real backup/user data.

The caller also provides an expected compartment and a synthetic `checkpoint = { epoch, revision }`; if the manifest epoch is older or its revision is not strictly newer at the same epoch, the fixture fails as stale/replayed. **Neither the checkpoint nor the fixture manifest is authenticated.** An attacker who controls both the checkpoint and data can fabricate a passing fixture. The index SHA-256 is corruption evidence within the lab, not a signature, device authorization, live CAS, independent witness or rollback-resistant monotonic state.

The checker rejects a bounded list of explicit suspect indicators (`ROOTARK_TEST_PLAINTEXT_MARKER`, PEM private-key heading, and JSON-like key/password/plaintext/recovery-secret labels). These are heuristic signals; passing this filter **does not prove absence of plaintext or cryptographic key material**, that an envelope is authenticated or decryptable, that there are no copies outside the synthetic directories, or that a real backup has been safely classified. Tests contain synthetic markers and dummy bytes only.

## Evidence and exact limits

The targeted `test/issue-65-zk-backup-pre-restore-fixture.test.js` covers normal synthetic detection with unchanged file contents/timestamps, all required versions/copies/envelopes, corrupted or missing data, extra unlisted copy, stale/replayed epoch/revision, wrong compartment, canonical JSON/duplicate-field failure, malformed version ancestry and duplicate IDs, paired owner/recovery alias, traversal, symlinks, hardlinks, unsupported metadata, suspected plaintext/key-like markers and refusal to open real ZIPs or out-of-temp files. Local ciphertext migration journal at `src/services/zk1LocalFixtureMigrationJournal.js` remains independent and unmodified.

**Permanent blocking reasons returned with every result:** `missing-trusted-cas-witness`, `missing-owner-approved-recovery-policy`, `missing-authorized-client-decryption-proof`, and `missing-production-backup-restore-fence`. Before any live restore, Root.ark still needs production authority for CAS+witness monotonic version/epoch claims and replay, owner-approved migration/recovery policy, signed authenticated envelopes bound to expected scope and device state, actual authorized-client decrypt-and-verify, a protected backup/restore execution fence, and verified cross-provider backup/trash/version/derived-data inventory. The existing legacy ZIP schema cannot be promoted into a ZK restore authorization on the strength of this offline experiment.

No existing backup archive, cloud service, live database, original ciphertext, production route, or user data was read or modified.
