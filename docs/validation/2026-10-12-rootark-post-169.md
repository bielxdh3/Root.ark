## Restore semantics and remaining boundaries

Whole restore validates the archive/provider context, stages and verifies local pre-images under a durable coordinator, then applies quarantine, JSON data, uploads, SQLite, provider suppression/queue state, and backup history in order. The durable `restart_required` marker is written last. A caught failure after local mutation begins does not synchronously compensate inside the request: the coordinator and request barrier remain, and startup performs reverse-order, idempotent pre-image recovery before admitting requests. This can require a server restart after an in-process restore error. A failure after the `restart_required` marker instead follows forward recovery: migrations and durable provider reconciliation resume while the barrier remains active. Provider operations are persisted and retried idempotently; provider failure retains pending state rather than silently clearing it.

The independent restore-model audit at exact SHA `b62da94` found no actionable defect. It inspected `services/restoreService.js`, `services/restorePreimage.js`, startup gating, and restore failure tests. Two focused failure-injection selections passed, covering 11 selected tests with 0 failures; the exact-SHA full test suite also passed in both CI platforms. Tested boundaries include failures before local commit, quarantine and tree rollback interruptions, JSON/upload copy interruption, SQLite replacement/journal recovery, migration failure after commit, provider queue persistence and retry across restart, and startup recovery ordering.

This is crash-recoverable local coordination, not whole-restore atomic visibility. External writers outside the application gate can observe intermediate local changes; cloud APIs cannot join a portable filesystem/SQLite transaction; portable Windows directory-entry power-loss durability cannot be promised. Missing/corrupt pre-images or persistent recovery storage errors can require manual recovery. Live cloud-provider interoperability and production topology remain unverified. Browser acceptance covered restore confirmation, not an end-to-end destructive restore followed by restart.
