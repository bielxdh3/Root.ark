# Root.ark #65 — shared PostgreSQL gate and protected ciphertext-write integration

**Date:** 2026-10-21
**Parent commit:** `32d38c1`
**Scope:** isolated opt-in PostgreSQL-only reference data plane; **NOT** the production ZK-1 release

## Implemented

`db/zk1-gate-authority.sql` defines a durable shared head, active-admission ledger and ciphertext chunk table. `Zk1SharedPgGateAuthority` uses one PostgreSQL primary and a row lock on the exact head for START, QUIESCING, FINISH, PENDING and each **physical PostgreSQL ciphertext INSERT**. A separate TLSv1.3/mTLS listener enforces scoped certificate fingerprint and role grants; the new strict mTLS client additionally pins the server certificate and refuses unexpected replies, non-2xx outcomes and timeouts. The new `Zk1SharedPgCiphertextSink` gives the trusted gateway a bounded write-only adapter: one worker per upload, per-chunk gate checks, idempotent same-worker START/PUT retries on lost response, explicit expected chunk count, exact acknowledgement validation, and FINISH in a finally block on completion or failure.

The schema now also creates a **non-login `zk1_gate_runtime` role** with schema USAGE/SELECT and limited column-specific INSERT/UPDATE grants required by the trusted gate implementation. It cannot update the head revision/digest or DELETE/TRUNCATE ciphertext. The disposable real-PG test uses `SET LOCAL ROLE` to prove both successful locked/admission operations and denied raw revision modification/deletion. **Operator setup must independently create a login authorized for this role, isolate its credentials from the web app, and prove that all deployments actually use the role.** Granting the trusted gate runtime state-transition column updates remains a trust boundary: a compromised gate process or DB administrator can manipulate the gate, so this is **not independent SQL state-transition enforcement**.

**2026-10-21 further operator-runtime gate:** `zk1SharedPgGateRuntime.js` exposes `verifyZk1SharedPgRuntimePool()` and an asynchronous, opt-in server factory. Before any TLS listener is created, it verifies the live PostgreSQL session/current user is the same dedicated **LOGIN** identity, is not a superuser, has neither create-role nor create-database capability, inherits the non-login `zk1_gate_runtime` privileges, can operate the gate head's phase but cannot rewrite its revision or delete/truncate ciphertext, and cannot create objects inside `zk1_gate`. Unknown privileges, query errors and privileged application/admin connections fail closed. The disposable PG runner creates a fresh random login/password only in its isolated container and runs the **real shared gate Node implementation using that restricted account**, proving START, physical ciphertext INSERT, QUIESCING, FINISH and PENDING plus denied raw revision UPDATE and DELETE. Test credentials never leave the disposable lab's process environment; container identity is verified before cleanup. This proves the operational preflight and role-level restrictions in one primary, not independent trusted operator management or a tamperproof state machine.

The reviewer identified unqualified SQL catalog references as a potential preflight spoofing surface. The runtime identity query now fully qualifies `pg_catalog.pg_roles` and all PostgreSQL privilege-checking functions. A real-PG regression creates a forged `pg_temp.pg_roles`, places `pg_temp` first on `search_path`, and proves the privileged login **still fails** identity verification. ## Strict trust boundaries and known omissions

This experiment is **not** the complete distributed GateAuthority contract. A single PG primary shared by separate processes demonstrates cross-process transactional ordering but not a deployed, independently owned, multi-failure-domain consensus/storage system. The schema includes a limited non-login role but **does not verify operational login identity and connection provenance**, block trusted runtime mutation of gate phase/generation, or provide operator-pinned anti-rollback state. The laboratory uses disposable superuser credentials to seed initial scopes and privileged test fixtures. No live user files or credentials are involved.

No public Root.ark legacy upload, download, versions, sync, backup/restore, WebDAV, S3 or Google Drive route is reclassified or routed through this gate. The sink is only usable after an **independent trusted caller** has verified user/session permissions, signatures and the exact ZK keyring/manifest binding. The current listener deliberately has **no GET/egress endpoint** and denies GET admission: it is not safe to stream network ciphertext while holding a PostgreSQL row lock inside an asynchronous JavaScript callback, because a severed SQL connection may release the lock before the socket stops writing. There is no remote stop attestation beyond the gateway's authenticated FINISH assertion, no independent data-plane stop ACK, signed ticket/CAS terminal-proof integration, external-provider fencing or reversible legacy migration. A double-lost START acknowledgement may strand a durable admission fail-closed until authenticated operator reconciliation. No epoch/token revocation protects already exported ciphertext.

An independent adversarial reviewer **reproduced this network-egress defect as a P1** against the earlier experimental callback: after killing its PostgreSQL backend, another authority completed QUIESCING while the old callback still emitted ciphertext, and the old request failed only at its later COMMIT. The unsafe public callback and all GET/egress routes were removed rather than presenting a mere post-hoc error as physical fencing. The bounded final independent review reported **PASS with no confirmed P1/P2** in the remaining PostgreSQL-write-only and pinned-mTLS-sink scope; this is *not* issue-wide acceptance.

Do not enable the experimental endpoint as production Zero-Knowledge storage without real provider enforcement, genuinely independent status and witness authorities, signed request/receipt binding, end-to-end security review and distributed failure tests.
