## Restore transaction model and residual boundary

Before the first restore mutation, Root.ark validates the archive/manifest and quarantine input, stages and verifies a durable preimage, and writes the whole-restore coordinator. Locally controlled domains include quarantine state, restorable data files, uploads, SQLite files/sidecars, backup metadata, and provider-suppression policy. Restore applies these domains in sequence. A failure before the local commit boundary triggers reverse-order rollback. If the process stops, startup verifies the coordinator and preimages and resumes rollback before accepting requests; missing or corrupt recovery data keeps the service blocked for manual recovery. After the local commit boundary, migrations and configured restart acknowledgements complete behind the durable request/WebSocket barrier. Provider synchronization then drains the persisted idempotent reconciliation queue; failed provider actions keep the coordinator/recovery state and affected objects fenced for retry.

This is not a single atomic switch: external writers that bypass application barriers can observe or cause intermediate local state; rollback may require manual recovery after storage failure, permission loss, or interference; cloud APIs cannot participate in the local filesystem/SQLite transaction; and Node.js does not expose a portable Windows directory-entry flush for equivalent power-loss durability. Local provider-reconciliation records are durable, but live S3/Google interoperability and production topology were not demonstrated. Failure injection uses disposable fixtures. The [restore transaction boundary](../backup-restore-transaction-boundary.md) contains the full limitations and test model. No claim of fully atomic restore or production readiness is made.
