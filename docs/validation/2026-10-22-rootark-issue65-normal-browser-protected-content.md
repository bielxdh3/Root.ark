# Issue #65 — bounded normal browser protected-file path (2026-10-22)

Development-only UI: `/zk1-protected-file-lab.html`, served only when
`ROOTARK_ZK1_CONTENT_CONFIG` is configured and `NODE_ENV` is not production.
The underlying protected routes independently enforce the normal account session
and upload/list permissions, Ed25519 operation signatures, and their configured
CAS/witness/signed-history admission. No legacy file route or recovery flow changes.

## Offline authority contract

The browser requires **three independent trust inputs** before generating a CEK:

1. A 32-byte raw Ed25519 owner public key selected from outside the server,
   plus the externally pinned base64url SHA-256 **of those raw 32 bytes**.
2. An externally checked current head (revision, manifest digest, keyring epoch).
   The server must not supply these values as their sole source of truth.
3. An owner-signed, exact-field, bounded device grant for the **same head**.
   Its key ID and 32-byte public key must match the supplied local device key,
   `enrolled_epoch <= current_epoch`, and `revoked_at_epoch === null`.
   The local nonextractable Ed25519 private key must prove possession.

The grant is a *lab-only owner attestation*, **not** the canonical zk-1 v2
recovery manifest, a full signed-transition-history verifier, an online
revocation oracle, or a replacement for the server's independent checks.
Its canonical serialization is UTF-8
`Root.ark/zk-1/browser-owner-device-grant/v1\0` followed by the JSON string of
these keys, in exactly this order:

```
schema, account_id, compartment_id, keyring_id, device_id,
authorization_key_id, authorization_public_key, manifest_revision,
manifest_digest, current_epoch, enrolled_epoch, revoked_at_epoch
```

The signature is Ed25519 over that message, encoded as canonical base64url
under the additional `signature` JSON field. `schema` is
`rootark-zk1-browser-owner-device-grant/v1`. Scope identifiers, the device
authorization key ID, public key and manifest digest are canonical base64url.
The owner must issue a new grant after trusted history advances. The grant is
expected to be generated by an independently trusted, owner-controlled signing
process; there is intentionally no API to ask Root.ark to mint the grant.

The dev UI reads raw owner/device public keys, local device PKCS#8, signed
grant JSON, manually pinned current revision/digest/epoch and a selected file.
It imports the private key as **nonextractable**, encrypts the content plus
filename/media type using a fresh nonextractable AES-GCM CEK, and writes it
through the protected normal account PUT route. A historical signed GET checks
the exact returned object/revision/epoch, ciphertext digest, locally calculated
chunk root and decrypted plaintext. No CEK, plaintext or original filename is
sent to the protected route. On a lost PUT response, it **only** attempts a
new signed historical GET; it never retransmits the PUT.

## Deliberate limits

- The out-of-band pin's *freshness* and owner operator custody cannot be
  established by a static browser form. A compromised/stale pin can cause
  stale reads unless the server's independent online authority rejects them.
- This is a single immediate PUT and GET verification of a newly created
  object. The random CEK is intentionally not persisted or exported. **Data
  cannot be reopened after the page finishes or reloads.** This is not a
  durable end-user file workflow.
- No off-host durability, rollback-resistant external checkpoint, independent
  multi-host witness/gate execution, multiprovider restore, recovery wrap,
  device lifecycle UI, safe edit/version lifecycle, or production cutover is
  claimed.
- The owner grant is a temporary supplementary browser proof and **must not**
  become the production authority format without an approved canonical history,
  provisioning, and offline owner-key custody protocol.

## Evidence

Run on Windows with the dependencies from a compatible clean checkout:

```powershell
node --test test/issue-65-normal-browser-protected-content.test.js
```

The tests exercise real localhost Express protected PUT/GET with cryptographic
browser operations, plus an actual headless Edge execution over HTTP with
`script-src 'self'`. They check owner pin and head mismatch, tampered grant,
missing/revoked device, device private-key mismatch, cross-epoch and cross-scope
metadata, revocation after the browser pin, lost PUT ACK with **one PUT**, and
forged GET ciphertext/object ID/epoch. The synthetic test witness is not proof
of physical operator separation or external storage durability.
